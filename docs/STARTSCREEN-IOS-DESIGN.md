# Рабочий стол (Start Screen) Windows Phone 10 для iOS — проектный дизайн

> Проектный документ: теоретическое проектирование компонента «Рабочий стол» по мотивам Windows 10 Mobile для iOS.
> Ограничения: **iOS 15+**, **Swift 5.9+**, допускаются UIKit и SwiftUI. Реализация в объём документа не входит.
> Парные документы: **PANORAMA-IOS-DESIGN.md**, **PIVOT-IOS-DESIGN.md**. Общие механики (пейджер, параллакс, арбитраж жестов) вынесены в общий слой: **CORE-IOS-DESIGN.md** (пакет **TesseraKit**, target `TesseraCore`).

## 0. Что проектируем

Рабочий стол Windows 10 Mobile (Start Screen):

- вертикальный скролл плиток + фоновые обои с параллаксом;
- live-плитки: флип (двусторонние), бейджи, живой контент;
- плитки 4 размеров: small 1×1, medium 2×2, wide 4×2, large 4×4;
- **свайп справа налево → список приложений (там же настройки)**;
- **свайп слева направо → хук вызова чего угодно** (в WP10 этого не было — расширение проекта);
- режим редактирования: «желе», unpin, resize, перетаскивание.

## 1. Ключевая архитектурная идея: три страницы

Горизонтальный мир рабочего стола — это **пейджер из трёх полноэкранных страниц**:

```
[ Левая страница (хук) ]  [ START ]  [ Все приложения + Настройки ]
```

Start — центральная, с неё свайп справа налево уводит в список приложений (в точности WP), слева направо — на страницу-хук. Всё, что спроектировано для Pivot, работает здесь без изменений: `UIScrollView.isPagingEnabled = true`, полноэкранные страницы — бесплатный снап, тот же инвариант `t = offset.x / pageWidth`. **Ядро Pivot переиспользуется почти дословно** — сильный аргумент за выделение общего core-пакета (см. §12).

Два нюанса против Pivot:

1. **Арбитраж жестов становится трёхсторонним**: пейджер хочет горизонталь, плиточная сетка — вертикаль, список приложений — вертикаль. Решение то же (вариант B из Panorama): в `gestureRecognizerShouldBegin` пейджера отдаём жест по доминирующей оси — горизонталь пейджеру, вертикаль ребёнку. Разница только в том, что правило применяется к двум детям.
2. **Левый край экрана занят системой**: если компонент живёт внутри `UINavigationController`, свайп слева направо дерётся с `interactivePopGestureRecognizer`. Политика: рабочий стол — **корневой экран без back-навигации** (как на WP), тогда оба края наши; если вложен в стек — системный жест отключаем или уступаем ему. Это ровно тот конфликт, который разбирался с edge pan.

## 2. Архитектура

```
StartScreenView (SwiftUI-фасад)
    └─ StartScreenViewController (UIKit)
        ├─ HorizontalPager (3 страницы, ядро Pivot)
        │    ├─ QuickPanelPage        ← левая страница-хук (пустая по умолчанию)
        │    ├─ StartPage
        │    │    ├─ TileGridView      ← UICollectionView + кастомный layout
        │    │    └─ TileBackgroundView ← обои + вертикальный параллакс
        │    └─ AppsListPage          ← jump-list приложений + настройки
        ├─ LiveTileEngine             ← таймеры флипа, контент-провайдеры
        ├─ TileEditCoordinator        ← железо, drag, resize, unpin
        └─ TileStore                  ← порядок/размеры, персистентность
```

Модель:

- `TileDescriptor` — id, размер (4 вида), контент (статичный или провайдер), позиция в сетке;
- `TileLayoutEngine` — раскладка в юнитах;
- `LiveTileContentProvider` — источник «живого» контента (фронт/бэк, обновления);
- `StartScreenDelegate` — события (тап, pin/unpin, переходы страниц, хук).

## 3. Плиточная сетка — самая сложная часть

**Модель раскладки.** Сетка `N` колонок (4 по умолчанию, опция 6 для больших экранов). Юнит:

```
unit = (screenWidth - margins - gaps × (N-1)) / N
```

Размеры плиток в юнитах: 1×1, 2×2, 4×2 (wide), 4×4 (large). Позиция хранится в **юнитных координатах** — тогда сетка автоматом пересчитывается под любую ширину экрана (поворот/iPad), а раскладка не зависит от пикселей.

**Алгоритм упаковки**: жадный, слева направо сверху вниз — ищется первая строка, куда прямоугольник плитки помещается целиком. **Дыры допускаются честно**: в WP10 они существовали (под wide/large плитками оставались пустые юниты). Это сильно упрощает алгоритм — никакого «идеального тетриса».

**Реализация** — кастомный `UICollectionViewLayout`:

- `layoutAttributes` считаются из модели (юниты → rect);
- изменения (resize, reorder) — через инвалидацию с контекстом + `performBatchUpdates`, тогда сдвиг соседних плиток анимируется UICollectionView сам;
- правило производительности из Panorama свято: в `scrollViewDidScroll` **только параллакс фона, никакого layout**.

**Почему не готовый flow-layout**: переменные размеры + «выталкивание» при перетаскивании + WP-вид сдвига — готовые layout'ы этого не дают, а кастомный тут выходит проще, чем подгонка.

## 4. Live-плитки (движок)

- **Контентная модель**: у плитки фронт (иконка/заголовок/счётчик/фон) и опциональный бэк. `LiveTileContentProvider` отдаёт контент и подписки на обновления (таймер, пуш, фаза сцены).
- **Флип**: контейнер с двумя слоями, `CATransform3D` + перспектива (`m34`), поворот по Y на 90°, подмена стороны, доворот. Только трансформы — layout не трогаем.
- **Стахгер**: плитки флипаются не одновременно, а батчами со случайным разбросом (у WP именно так; синхронный флип всего экрана выглядит дёшево).
- **Паузы**: плитка вне экрана (`layoutAttributes` видимости) — флип заморожен; приложение в фоне — заморожен; **Reduce Motion включён — флипов нет вообще**, показывается статичный фронт.
- **Бейдж** — маленький счётчик в углу (отдельный view, не часть флипа).
- Память: изображения декодируются в размер плитки и кешируются, иначе десяток живых плиток съест сотни мегабайт.

## 5. Режим редактирования

Три подзадачи, по возрастанию сложности:

1. **Вход и «желе»**: long-press → все плитки трясутся (как iOS home). Джиттер — `CAKeyframeAnimation` поворота ±2° на каждую плитку со случайной фазой; при Reduce Motion — не трясутся, только подсветка/X-кнопки.
2. **Unpin и resize**: крестик — открепление с fly-out анимацией; стрелка — циклическая смена размера (small → medium → wide → large → small, с учётом поддерживаемых плиткой размеров). Resize запускает переупаковку (п. 3) с анимацией.
3. **Перетаскивание** — самая багогенерирующая часть: снэпшот плитки едет за пальцем, соседние плитки «расступаются» с анимацией, при отпускании плитка встаёт в ближайшее валидное место. Стратегия: **собственный drag-координатор** (снэпшот + пустышка + переупаковка модели + инвалидация layout), а не нативный `UICollectionView` interactive movement — нативный заточен под равные ячейки и на переменной сетке даёт рваные анимации.

`TileStore` сохраняет порядок/размеры/закрепления (JSON/файл), выживает между запусками.

## 6. Страница справа: список приложений + настройки

- `UITableView` с секциями по буквам + `sectionIndexTitles` (jump-list) — нативный паттерн, ничего изобретать не надо.
- **Настройки — секция/элемент списка** (как на WP), при желании отдельный экран настроек внутри этой же страницы.
- **Двусторонняя связь с плитками**: pin из списка → плитка появляется в сетке; unpin на сетке → элемент списка меняет состояние. Источник истины — `TileStore`, обе страницы только читают/пишут его — то же правило «один писатель», что в Pivot.

## 7. Страница слева: хук

- Контейнер с протоколом `QuickPanelProviding` (или замыканием) — по умолчанию пустая заглушка.
- Примеры наполнения: быстрые настройки, поиск, профиль, недавние приложения — всё, что захочет приложение.
- Механика: пейджеру всё равно, что на странице; хук получает колбэки появления/скрытия, чтобы подгружать контент лениво.

## 8. Параллакс фона

Переиспользуется подход Panorama, но по вертикали: обои выше `contentSize` сетки, в `scrollViewDidScroll` — `backgroundOffset = offset.y × factor` (factor ≈ 0.4–0.6), только `frame`/`transform`. При Reduce Motion — статично. Направление на экране и расположение слоя — см. «Отступления реализации», п. 6.

## 9. Accessibility

- **Плитка** — один элемент: label из заголовка + состояния (счётчик), `UIAccessibilityCustomAction` для resize/unpin; в режиме редактирования озвучивается смена режима.
- **Страницы**: листание через `accessibilityScroll`; название страницы озвучивается.
- **Reduce Motion**: нет флипов, желе, параллакса.
- **Dynamic Type**: текст плиток и списка масштабируется; проверять, что на small-плитке текст усекается корректно.
- **RTL**: зеркалится сетка, пейджер и jump-list.

## 10. MVP и что отрезать

**Входит:**

1. Пейджер трёх страниц (ядро Pivot).
2. Сетка: 4 размера, жадная упаковка, кастомный layout.
3. Edit-режим: желе, unpin, resize, drag-перестановка.
4. Live-флип для простых текстовых плиток + бейджи + стахгер + паузы.
5. Список приложений с буквами + секция настроек, двусторонний pin/unpin.
6. Левая страница-хук.
7. Обои + параллакс.
8. SwiftUI-фасад, VoiceOver + Reduce Motion, персистентность TileStore.

**Отрезано в v1:** фото-слайдшоу в плитках, push-обновления контента, «идеальная» упаковка без дыр, peek-анимация, 6-колоночная адаптация, deep-links из плиток.

## 11. Риски

- **Drag-перестановка на переменной сетке** — главный источник багов; закладывать тесты на случайных конфигурациях плиток.
- **Жестовый стек** — самый сложный в проекте: горизонтальный пейджер × вертикальная сетка × вертикальный список × системный жест слева. Разруливается правилом доминирующей оси + политикой «корневой экран».
- **Флипы vs скролл** — джиттер при неаккуратной реализации; лечится только трансформами и паузами.
- **Культурный риск**: живой рабочий стол — самая «чужая» для iOS вещь из всех трёх компонентов; только как опциональный режим, не как дефолтная навигация.

## 12. Структура проекта: общий Core

У трёх компонентов накопился общий слой: инвариант `t`, пейджер с `pagingEnabled`, арбитраж жестов (вариант B), правило «никакого layout в скролле», SwiftUI-фасад. Предлагаемая структура (детали и контракты — в **CORE-IOS-DESIGN.md**):

```
TesseraKit (SPM-пакет)
├── TesseraCore        ← пейджер, параллакс, арбитраж жестов, фасады
├── TesseraPanorama    (свой снап, peek, фон)
├── TesseraPivot       (лента заголовков, индикатор)
└── TesseraStartScreen (сетка плиток, live-движок, 3 страницы)
```

## 13. Итог

Рабочий стол — композиция уже спроектированных механик (пейджер Pivot, параллакс Panorama, вариант B для вертикали) плюс два по-настоящему новых «монстра»: плиточная сетка с переменными размерами и live-движок. Сложность концентрируется в трёх точках: жадная упаковка в юнитах, drag-перестановка с анимацией «расступания» и дисциплина флипов (только трансформы, стахгер, паузы). Если эти три точки выдержать, остальное собирается из уже готовых деталей.

## 14. Уточнения MVP (29.10.2026)

Решения пользователя, уточняющие этот документ перед реализацией (полные формулировки — D12–D15
в [STATE.md](STATE.md)):

1. **Рабочий стол — ярлыки и папки.** Компонент выглядит как рабочий стол с ярлыками и папками;
   ярлык — **просто действие**: `id`, `title`, `icon`, `action: () -> Void`, опциональный `badge`
   (красная точка/счётчик внимания — как на WP). Поля `type` у ярлыка нет, группировка по типу
   не используется.
2. **Обе боковые страницы опциональны.** Левая (хук, `QuickPanelProviding`) и правая (список
   приложений/настроек) существуют, только если хост их задал; пейджер масштабируется от 1
   страницы (только START) до 3.
3. **Папки — через функцию одобрения.** Создание папки, добавление ярлыка в папку и перемещение
   между папками разрешает колбэк хоста (дефолт — разрешено).
4. **Live-плитки закладываются** (флипы, стахгер, паузы, Reduce Motion — §4 без изменений);
   размеры ярлыков — **4 вида**: 1×1, 2×2, 4×2, 4×4.

## Отступления реализации (v0.1, 29.10.2026)

> Сверка проектного документа с фактическим кодом релиза 0.1.0. Текст выше не переписывался: отступления зафиксированы отдельной секцией. Формат пункта: что обещал документ → что делает код → решение.

1. **§5 «Режим редактирования»: кто его подключает.** Документ (и схема §2) обещал, что редактирование — часть экрана: `TileEditCoordinator` внутри `StartScreenViewController`, long-press входит в режим «желе». Код: `TesseraStartScreenViewController` и `StartScreenView` координатор не создают и собственного API входа в редактирование не имеют — наружу открыта только сетка (`gridView`) как точка подключения координатора. Хост сам создаёт `TileStore` и `TesseraTileEditCoordinator(grid:store:configuration:)`, передавая сетку экрана (`public var gridView` контроллера), а координатор в инициализаторе сам вешает на неё long-press (0.45 с) и tap по фону; дальше хост вызывает `beginEditing()`, `endEditing()`, `toggleEditing()` тогда, когда считает нужным. Решение: в v0.1 режим редактирования — хост-опция поверх готовой сетки; владение координатором экраном отложено (так приложение, которому редактирование не нужно, не платит за координатор и его оверлеи).

2. **§2/§6 «Страница справа» и принадлежность `TileStore`.** Документ обещал: `AppsListPage` — часть экрана, `TileStore` — компонент экрана (схема §2), настройки — «секция/элемент списка». Код: правая страница — произвольная фабрика `() -> UIViewController` (решение D13); `TesseraAppsListPageViewController` — опциональный готовый класс (`make(store:settings:texts:)`), который хост может не использовать вовсе. Экран данных не хранит: `TesseraStartScreenViewController.configure(leftPanel:rightPage:)` и `StartScreenView.init(snapshot:style:leftPanel:rightPage:...)` принимают готовый снимок сетки (`TileGridSnapshot` через `reload(grid:)` в UIKit и `snapshot:` в SwiftUI), `TileStore` не создаётся и не удерживается. Настройки — строки хоста (`TesseraAppsListSettingsItem` с `id`/`title`/`subtitle`/`icon`/`action`), компонент не знает их смысла. Решение: `TileStore` живёт у хоста (единственный писатель), экран — презентационный слой; схему §2 читать как предлагаемую компоновку приложения, а не как состав библиотеки.

3. **§2 «Модель»: фактический состав `StartScreenDelegate`.** Документ обещал события «тап, pin/unpin, переходы страниц, хук». Код: в протоколе четыре события — `startScreen(_:didTapShortcut:)`, `startScreen(_:didTapFolder:)`, `startScreen(_:didChangePage:index:)`, `startScreen(_:didChangeHookVisibility:)`, все с пустыми реализациями по умолчанию (обязательных нет). Pin/unpin в делегате отсутствует: закрепление — операция модели (`TileStore.pin`/`unpin`, в том числе из опциональной страницы списка), а режим редактирования сообщает об откреплении через `TesseraTileEditCoordinatorDelegate` (`tileEditCoordinator(_:didUnpin:)` и соседние события resize/move/папок). Тап по ярлыку — событие, а не вызов `TileDescriptor.action` (D12): действие выполняет хост. Решение: актуальный контракт — четыре события выше; pin/unpin и редактирование — в `TesseraTileEditCoordinatorDelegate`; перечисление §2 оставлено как проектное намерение.

4. **§2/§3 «Модель раскладки»: где живут координаты.** Документ обещал: «Позиция хранится в юнитных координатах». Код: `TileStore` хранит только порядок элементов сетки (`gridOrder`), авторитетные размеры (`sizes`, размер папки в `FolderRecord`) и папки; `TileGridSnapshot.layoutItems` — пары «id + размер» в порядке сетки, без колонок и строк. Юнитные координаты вычисляются заново при каждой раскладке: `TesseraTileCollectionViewLayout` вызывает `TileLayoutEngine.unit(screenWidth:columns:gaps:)`, затем `TileLayoutEngine.pack(items:columns:unit:)` и `TileLayoutEngine.rect(for:unit:gap:origin:)`. То есть колонка/строка — производные от порядка, размеров и доступной ширины. Решение: координаты не персистятся — именно это делает поворот/iPad бесплатными; §3 в этой части трактуем как описание вычисляемой раскладки, а не формата хранения.

5. **§3 «Плиточная сетка»: «честные дыры» отменены — финальная раскладка строго компактная (E8.5).** Документ обещал жадную упаковку, в которой «дыры допускаются честно»: под wide/large плитками остаются пустые юниты, пока в них не поместится следующая плитка. Код: `TileLayoutEngine.pack` (публичный вход; реализация — `packCompact`) ставит каждую плитку в самую верхнюю-левую позицию, где она помещается целиком, и затем схлопывает раскладку вверх-влево до неподвижной точки (`stabilize`): ни одну плитку нельзя сдвинуть вверх или влево, пустых строк не остаётся. Свободный юнит остаётся только там, куда не помещается ни одна из **текущих** плиток (например, справа от 2×2, если следующая — 4×2); как только появляется плитка подходящего размера, она занимает это место, а после перетаскивания или открепления нижние плитки поднимаются в освободившееся место. Строгая компактность применяется и к обычной раскладке, и к edit/drag-переупаковке (обе идут через `pack`), поэтому визуал режимов не различается; панель раскрытой папки (D17) по-прежнему не упаковывается как плитка — она полноширинная строка под полосой папки (п. 11), а элементы под ней переупаковываются компактно. Решение: §3 в части «честных дыр» не действует — по спеке WP финальная раскладка компактна сверху вниз (PLAN E8.5); отступление зафиксировано здесь. Тесты: `TileLayoutEngineTests` — `assertCompactPacking`, схлопывание и reflow после утаскивания.

6. **§8 «Параллакс фона»: направление и расположение слоя обоев (E10.7б, W1, 30.10.2026).** Документ задавал `backgroundOffset = offset.y × factor` и «обои выше `contentSize`», не уточняя знак на экране и сторону запаса. Код: `TesseraParallaxLayer` (Core) лежит рядом со скроллом сетки, а не внутри него, и проецирует смещение на экран со знаком минус (`transform = −offset × factor`): при прокрутке вниз обои уезжают вверх вместе с плитками, но медленнее (до W1 обои ехали навстречу). Страница START ставит начало слоя на `padding` выше вьюпорта (поле под «резину» над верхом), а весь ход фона (`maximumOffsetY × factor`) и нижнее поле — ниже; вьюпорт закрыт при offset ∈ [−padding/factor, maximumOffsetY + padding/factor]. Решение: формулу §8 читать как смещение в координатах контента, экранная проекция — `−backgroundOffset` (Core, «Отступления реализации», п. 8); направление покрыто тестом `StartWallpaperParallaxTests`.

7. **Модель: индексы операций — видимые (E10.3a/b, W2, 30.10.2026).** Документ не различал «порядок сетки» и «то, что видно на экране». Код до W2: `TileStore.move(_:toIndex:)` и `pin(_:at:)` считали индексы в `gridOrder`, где после сокращения каталога остаются невидимые ключи (ярлыки вне каталога), а drop/превью работают в видимых индексах — плитка вставала не туда, а делегат `didMove` получал неверный индекс. Код после W2: индексы `move`/`pin(at:)` и новых `moveItem(_:toIndex:columns:) -> Int?`, `pinTile(_:at:columns:) -> Int?` — в пространстве видимого снимка; невидимые ключи остаются на своих позициях в `gridOrder`; новые перегрузки возвращают фактический видимый индекс. Решение: публичный контракт индексов `TileStore` — видимые индексы снимка; координатору (W4) — перейти на `moveItem(..., columns:)` и отдавать делегату возвращённый индекс. Тесты: `TileStoreVisibleOrderTests`.

8. **Модель: порядок модели = порядок чтения (E10.15, W2, 30.10.2026).** Документ считал порядок элементов и визуальный порядок одним и тем же. При строгой компактной упаковке (п. 5) более поздняя плитка может встать выше более ранней (`[medium A, wide W, small S]` читается A, S, W) — drag-индексы и порядок VoiceOver расходились с экраном. Код: после мутаций с известным числом колонок (`resize(_:to:columns:)`, `moveItem`/`pinTile` с `columns`) хранилище канонизирует видимый порядок к порядку чтения (строка, затем колонка слотов `pack`); одно изменение — один `onChange` и одна запись на диск; явный вход — `canonicalizeVisibleOrder(columns:)`, чистая функция — `TileStore.readingOrder(of:columns:)`. Решение: видимый порядок модели совпадает с экранным при известных колонках; хосту/координатору — вызывать `canonicalizeVisibleOrder(columns:)` после операций без колонок (unpin, папки, `setCatalog`, `load`). Следствие строгой компактности: в `[medium A, small S, wide W]` перенос S на место W визуально ничего не меняет. Тесты: `TileStoreVisibleOrderTests`.

9. **Персистентность: нечитаемый файл не затирается (E10.3d, W2, 30.10.2026).** Документ обещал персистентность `TileStore` без политики для повреждённого файла. Код до W2: повреждённый или записанный более новой схемой файл перезаписывался схемой v1 при первом автосохранении. Код после W2: такой файл до любой записи переименовывается в `<имя>.unreadable-<ISO-дата>.json` (при совпадении — суффиксы `-2`, `-3`, …), путь — в `lastUnreadableFileBackupURL`; `load()` по-прежнему бросает ошибку. Решение: данные пользователя не теряются молча; восстановление — забота хоста. Тесты: `TileStoreRecoveryTests`.

10. **Персистентность: чистка папок по каталогу после загрузки (E10.3c, W2, 30.10.2026).** Документ не описывал согласование файла с каталогом. Код: чистка выполняется и в `setCatalog`, и в `load()` — папка без ярлыков каталога распускается, неизвестные ярлыки удаляются из папок; осиротевшие папки из файла (нет в порядке сетки) встают в конец сетки. Решение: после загрузки в модели нет «мёртвых» папок и невидимых ключей внутри папок. Тесты: `TileStoreRecoveryTests`.

11. **Раскладка: панель папки — под «полосой папки» (E10.1, W2, 30.10.2026).** D17 обещал панель «под плиткой папки». Код до W2 решал «выше/ниже панели» по началу строки плитки (`slot.row < folderEndRow`): плитка, начинающаяся в строках папки и заканчивающаяся ниже, оставалась на месте и перекрывалась панелью. Код после W2: `TileLayoutEngine.folderBandEndRow(for:in:)` расширяет нижнюю границу строк папки до `max(row + unitRows)` всех пересекающих её плиток (итеративно) — это «полоса папки»; панель встаёт под полосой, плитки полосы и выше остаются на месте, плитки ниже переупаковываются компактно от `panelTop + panelHeight + itemSpacing`. Вход для индекса вставки — новая перегрузка `folderPanelInsertionIndex(items:columns:expandedFolderID:)` (старая — устаревший вход без полосы); `rowsBelowOffset` возвращает `panelHeight + spacing` (новый параметр `spacing`, по умолчанию 8). Решение: D17 уточнён в `STATE.md` («полоса папки»). Тесты: `FolderBandLayoutTests`, `FolderPanelInsertionTests` («ступенька» `[папка 2×2, small, small, ярлык 2×2]`).

12. **Раскладка: пиксельное выравнивание юнита (E10.1, W2, 30.10.2026).** Документ (§3) задавал юнит как `(ширина − зазоры) / колонки` без учёта пикселей — рамки плиток ложились на дробные пиксели. Код: `TileLayoutEngine.unit(screenWidth:columns:gaps:scale:)` округляет юнит вниз до `1/scale`, зазор — к ближайшему пикселю; остаток ширины делится на поля (левое — `floor(остаток/2)`, правое — остальное), сетка центрируется (`gridMetrics`). Масштаб — `traitCollection.displayScale` (fallback `UIScreen.main.scale`; `0` — без выравнивания); прежняя `unit(screenWidth:columns:gaps:)` не изменилась. Остаток: `magnetSlotCenters(for:)` в `TileGridView` считает невыровненный юнит (расхождение ≤ 1 pt) — PLAN E10.4 (W3). Тесты: `TileGridPixelAlignmentTests`.

13. **Раскладка: зазор панели папки = `itemSpacing` (E10.1, W2, 30.10.2026).** Код до W2 ставил зазор между панелью и соседними плитками жёстко 8 pt. Код после W2: зазор берётся из `itemSpacing` сетки (через `gridMetrics`), высота — `panelHeight(for:width:columns:spacing:scale:)`; внутренние поля панели (12 pt) и зазор «заголовок — сетка» (8 pt) остались константами. Решение: панель следует ритму сетки при любом `itemSpacing`; внутренние отступы панели — часть её стиля.
