# Рабочий стол (Start Screen) Windows Phone 10 для iOS — проектный дизайн

> Проектный документ: теоретическое проектирование компонента «Рабочий стол» по мотивам Windows 10 Mobile для iOS.
> Ограничения: **iOS 15+**, **Swift 5.9+**, допускаются UIKit и SwiftUI. Реализация в объём документа не входит.
> Парные документы: **PANORAMA-IOS-DESIGN.md**, **PIVOT-IOS-DESIGN.md**. Общие механики (пейджер, параллакс, арбитраж жестов) вынесены в общий слой: **CORE-IOS-DESIGN.md** (пакет **TesseraKit**, target `TesseraCore`).

## 0. Что проектируем

Рабочий стол Windows 10 Mobile (Start Screen):

- вертикальный скролл плиток + фоновые обои с параллаксом;
- live-плитки: флип (двусторонние), бейджи, живой контент;
- плитки 4 размеров: small 1×1, medium 2×2, wide 4×2, large 4×4;
- **свайп справа налево → список приложений (там же настройки)**;
- **свайп слева направо → хук вызова чего угодно** (в WP10 этого не было — расширение проекта);
- режим редактирования: «желе», unpin, resize, перетаскивание.

## 1. Ключевая архитектурная идея: три страницы

Горизонтальный мир рабочего стола — это **пейджер из трёх полноэкранных страниц**:

```
[ Левая страница (хук) ]  [ START ]  [ Все приложения + Настройки ]
```

Start — центральная, с неё свайп справа налево уводит в список приложений (в точности WP), слева направо — на страницу-хук. Всё, что спроектировано для Pivot, работает здесь без изменений: `UIScrollView.isPagingEnabled = true`, полноэкранные страницы — бесплатный снап, тот же инвариант `t = offset.x / pageWidth`. **Ядро Pivot переиспользуется почти дословно** — сильный аргумент за выделение общего core-пакета (см. §12).

Два нюанса против Pivot:

1. **Арбитраж жестов становится трёхсторонним**: пейджер хочет горизонталь, плиточная сетка — вертикаль, список приложений — вертикаль. Решение то же (вариант B из Panorama): в `gestureRecognizerShouldBegin` пейджера отдаём жест по доминирующей оси — горизонталь пейджеру, вертикаль ребёнку. Разница только в том, что правило применяется к двум детям.
2. **Левый край экрана занят системой**: если компонент живёт внутри `UINavigationController`, свайп слева направо дерётся с `interactivePopGestureRecognizer`. Политика: рабочий стол — **корневой экран без back-навигации** (как на WP), тогда оба края наши; если вложен в стек — системный жест отключаем или уступаем ему. Это ровно тот конфликт, который разбирался с edge pan.

## 2. Архитектура

```
StartScreenView (SwiftUI-фасад)
    └─ StartScreenViewController (UIKit)
        ├─ HorizontalPager (3 страницы, ядро Pivot)
        │    ├─ QuickPanelPage        ← левая страница-хук (пустая по умолчанию)
        │    ├─ StartPage
        │    │    ├─ TileGridView      ← UICollectionView + кастомный layout
        │    │    └─ TileBackgroundView ← обои + вертикальный параллакс
        │    └─ AppsListPage          ← jump-list приложений + настройки
        ├─ LiveTileEngine             ← таймеры флипа, контент-провайдеры
        ├─ TileEditCoordinator        ← железо, drag, resize, unpin
        └─ TileStore                  ← ячейки/размеры/папки, персистентность
```

Модель:

- `TileDescriptor` — id, размер (4 вида), контент (статичный или провайдер), позиция в сетке;
- `TileLayoutEngine` — раскладка в юнитах;
- `LiveTileContentProvider` — источник «живого» контента (фронт/бэк, обновления);
- `StartScreenDelegate` — события (тап, pin/unpin, переходы страниц, хук).

## 3. Плиточная сетка — самая сложная часть

**Модель раскладки.** Сетка `N` колонок (**6 малых по умолчанию** — три средние плитки в ряд, как в W10M, D26; хост может задать своё `columns`, например 4). Юнит:

```
unit = (screenWidth - margins - gaps × (N-1)) / N
```

Размеры плиток в юнитах: 1×1, 2×2, 4×2 (wide), 4×4 (large). При шести колонках wide занимает 4 из 6 (при четырёх заполняла бы весь ряд), large — 4×4. **Позиция — явная ячейка**: у каждого верхнеуровневого элемента (ярлык или папка) в модели есть `row`/`column` в логических юнитных координатах (0 — начало чтения, в RTL зеркалирует только вью-слой), плюс ширина холста `columns`, на которую они рассчитаны (D30, D33; схема `tiles.json` — §5). Юнитные координаты не зависят от пикселей, поэтому сетка пересчитывается под любую ширину экрана; смена ширины холста хоста даёт проекцию без дыр (D32, ниже).

**Раскладка по ячейкам (E14, D30–D33).** Плитка **якорится на своей ячейке**; обратного заполнения нет, **дыры настоящие**, как в W10M (W10M-STARTSCREEN §3): они остаются после открепления, слияния в папку, уменьшения плитки и drop'а. Строка схлопывается, только если её не занимает ни одна плитка (в том числе высокие), и только на drop или после открепления — не во время drag. Новая плитка (закрепление из списка приложений) встаёт в **новую строку в конце** холста, а не в дыру. **Коллизии** (drop на занятую клетку, рост плитки, слияние в папку 2×2 на месте малой плитки, распад папки — §5) разрешаются **выталкиванием вниз каскадом** (D31): мешающие плитки опускаются в своих колонках на нужное число строк, дыры вне затронутой области не трогаются; горизонтально никто не двигается. Ячейка ограничивается холстом (колонка только сдвигается влево), слишком широкая для сетки плитка ужимается. **Проекция (D32):** если сохранённая ширина холста отличается от `columns` хоста, сетка показывает репак по порядку чтения без дыр, файл не перезаписывается; возврат к прежней ширине возвращает дыры, первая правка принимает новую ширину. **Упаковка по порядку** (`TileLayoutEngine.pack`/`packCompact`: жадно, слева направо сверху вниз, строго компактно — отступление п. 5, E8.5) сохранилась только как запасной путь: откат раскладки, если таблица ячеек неполна или неприменима, миграция файла v1 → v2, проекция D32 и раскладка первого запуска. Панель раскрытой папки (D17) — полноширинная строка под «полосой папки»; плитки ниже полосы остаются на своих ячейках и сдвигаются вниз на высоту панели, без репака.

**Реализация** — кастомный `UICollectionViewLayout`:

- `layoutAttributes` считаются из модели (юниты → rect);
- изменения (resize, reorder) — через инвалидацию с контекстом + `performBatchUpdates`, тогда сдвиг соседних плиток анимируется UICollectionView сам;
- правило производительности из Panorama свято: в `scrollViewDidScroll` **только параллакс фона, никакого layout**.

**Почему не готовый flow-layout**: переменные размеры + «выталкивание» при перетаскивании + WP-вид сдвига — готовые layout'ы этого не дают, а кастомный тут выходит проще, чем подгонка.

## 4. Live-плитки (движок)

- **Контентная модель**: у плитки фронт (иконка/заголовок/счётчик/фон) и опциональный бэк. `LiveTileContentProvider` отдаёт контент и подписки на обновления (таймер, пуш, фаза сцены).
- **Флип**: контейнер с двумя слоями, `CATransform3D` + перспектива (`m34`), поворот по Y на 90°, подмена стороны, доворот. Только трансформы — layout не трогаем.
- **Стахгер**: плитки флипаются не одновременно, а батчами со случайным разбросом. Это собственное решение библиотеки (D36, 13.11.2026), а не копия поведения W10M: по референсу в 14393 плитки обновляются все сразу, но синхронный флип всего экрана выглядит дёшево.
- **Паузы**: плитка вне экрана (`layoutAttributes` видимости) — флип заморожен; приложение в фоне — заморожен; **Reduce Motion включён — флипов нет вообще**, показывается статичный фронт.
- **Бейдж** — маленький счётчик в нижнем углу у конца строки (правом в LTR, левом в RTL; D29, E15.1) — отдельный view, не часть флипа.
- Память: изображения декодируются в размер плитки и кешируются, иначе десяток живых плиток съест сотни мегабайт.

## 5. Режим редактирования

Четыре подзадачи, по возрастанию сложности:

1. **Вход и «желе»**: long-press → все плитки трясутся (как iOS home). Джиттер — `CAKeyframeAnimation` поворота ±1,2° за 0,4 с на каждую плитку со случайной фазой (в коде сейчас **включён** всегда); при Reduce Motion — не трясутся, только подсветка/X-кнопки. По решению D39 (13.11.2026) «желе» **станет выключенным по умолчанию** (в W10M сетка в правке статична) и будет включаться параметром `StartScreenStyle` на стороне хоста — **параметр будет в E15 (E15.6), пока не реализован**.
2. **Unpin и resize**: крестик (правый верхний угол, в RTL левый; D29, E15.2) — открепление с fly-out анимацией; стрелка (правый нижний угол) — циклическая смена размера small → wide → medium → large → small (D28, E15.3; с учётом поддерживаемых плиткой размеров). Resize идёт **на месте**: рост выталкивает соседей вниз (D31), уменьшение оставляет дыру (§3); открепление оставляет дыру, а пустая строка схлопывается сразу после него.
3. **Перетаскивание** — самая багогенерирующая часть: снэпшот плитки едет за пальцем, соседние плитки «расступаются» с анимацией, при отпускании плитка встаёт **на клетку под пальцем**. Стратегия: **собственный drag-координатор** (снэпшот + пустышка + превью на ячейках + инвалидация layout), а не нативный `UICollectionView` interactive movement — нативный заточен под равные ячейки и на переменной сетке даёт рваные анимации. Цель drag (E14.5): клетка под пальцем по **базовой** раскладке на момент захвата — пустая (плитка встаёт в дыру), занятая (цель и мешающие плитки выталкиваются вниз каскадом, D31), «новая строка» ниже последней занятой строки; центр плитки или папки (25 %) с удержанием 600 мс — слияние/добавление в папку. Превью каждый раз считается от базы (мешающие плитки уходят вниз), на слиянии и без цели показывается база; модель во время drag не меняется, запись — один раз на drop (`TileStore.moveItem(_:toCell:columns:)` и т. п., затем схлопывание пустых строк); отмена возвращает снимок на момент захвата. Drag из панели папки — те же цели (вынос на сетку, на другую папку, в «новую строку»).
4. **Папки.** Папка — верхнеуровневый элемент 2×2 (всегда medium при создании, D20) со своей ячейкой; создаётся слиянием (удержание над центром плитки), раскрывается инлайн под «полосой папки» (D17/D18, `folderTapHandler` позволяет хосту переопределить). **Папка не бывает из 0 или 1 ярлыка (D45):** когда из папки уходит предпоследний ярлык, папка распускается — оставшийся ярлык встаёт на её ячейку **со своим размером** (больший выталкивает соседей вниз, меньший оставляет дыру), пустая папка исчезает; хост узнаёт об этом из `didDissolveFolder(_:remainingTile:)`. Исключение — переходная папка публичного `createFolder(withTile:title:columns:)` до `addToFolder`. Перенос из папки в папку — один жест (D41).

`TileStore` сохраняет ячейки/размеры/закрепления/папки (JSON/файл `tiles.json`), выживает между запусками. **Схема — версия 2 (E14.1, D33):** у каждого верхнеуровневого элемента (ярлык или папка) есть явная ячейка `row`/`column` в логических координатах (0 — начало чтения), а в документе — ширина холста `columns`, на которую эти ячейки рассчитаны; `sizes` и `folders` прежние, ключи отсортированы, запись атомарная. Ячейки есть у верхнего уровня; содержимое папки координат не имеет. Файл версии 1 (ячеек нет) мигрирует **лениво и однократно**: `load()` идёт до того, как известна ширина сетки, поэтому первый вызов хоста с шириной (`TileStore.placeItems(columns:)`, его делает координатор редактирования; также любая операция с `columns`) прогоняет прежний `TileLayoutEngine.packCompact` по сохранённому порядку и сразу пишет версию 2 — внешне ничего не меняется; то же — раскладка первого запуска (посев каталога). Новые ключи каталога после появления ячеек встают в новую строку в конце холста, ярлыки вне каталога хранят ячейку, но в раскладке не участвуют и при возвращении занимают её, если она свободна, иначе — новую строку в конце. Если сохранённая ширина холста отличается от ширины хоста (D32), `placements(forColumns:)` отдаёт **проекцию** — репак по порядку чтения ячеек без дыр, — а файл не перезаписывается; возврат к прежней ширине без правок возвращает дыры, а первая правка принимает раскладку под ширину хоста как новый холст. При загрузке модель приводится к инвариантам: ячейки в границах холста, без пересечений видимых элементов (нарушители уходят в новые строки в конце); файл без ширины холста или с частичным набором ячеек читается как нераскладочный (дальше ленивая миграция). Версия новее поддерживаемой — как и раньше (резервная копия, состояние не меняется).

## 6. Страница справа: список приложений + настройки

- `UITableView` с секциями по буквам + `sectionIndexTitles` (jump-list) — нативный паттерн, ничего изобретать не надо.
- **Настройки — секция/элемент списка** (как на WP), при желании отдельный экран настроек внутри этой же страницы.
- **Двусторонняя связь с плитками**: pin из списка → плитка появляется в сетке; unpin на сетке → элемент списка меняет состояние. Источник истины — `TileStore`, обе страницы только читают/пишут его — то же правило «один писатель», что в Pivot.

## 7. Страница слева: хук

- Контейнер с протоколом `QuickPanelProviding` (или замыканием) — по умолчанию пустая заглушка.
- Примеры наполнения: быстрые настройки, поиск, профиль, недавние приложения — всё, что захочет приложение.
- Механика: пейджеру всё равно, что на странице; хук получает колбэки появления/скрытия, чтобы подгружать контент лениво.

## 8. Параллакс фона

Переиспользуется подход Panorama, но по вертикали: обои выше `contentSize` сетки, в `scrollViewDidScroll` — `backgroundOffset = offset.y × factor` (factor ≈ 0.4–0.6), только `frame`/`transform`. При Reduce Motion — статично. Направление на экране и расположение слоя — см. «Отступления реализации», п. 6.

## 9. Accessibility

- **Плитка** — один элемент: label из заголовка + состояния (счётчик), `UIAccessibilityCustomAction` для resize/unpin; в режиме редактирования озвучивается смена режима. У ярлыков панели папки — действия «Убрать из папки», «Переместить в папку…», «Открепить» (п. 37, 56). `.dot` озвучивается с E15.4 (D34), пока — нет.
- **Порядок обхода**: порядок индексов коллекции = порядок чтения ячеек (строка, затем логическая колонка; в RTL тот же), в том числе с дырами; панель раскрытой папки — после последнего элемента полосы папки. Фокус после операций правки (после unpin — следующий элемент в порядке чтения, после resize/drop/выноса — на изменённом, после слияния — на папке, после распада папки — на оставшемся ярлыке) — «Отступления реализации (E14)», п. 55–56. Порядок обхода по индексу коллекции выведен из кода и **на устройстве с VoiceOver не проверен** (R26, чек-лист «Ручная проверка E14» в PLAN.md).
- **Страницы**: листание через `accessibilityScroll`; название страницы озвучивается.
- **Reduce Motion**: нет флипов, желе, параллакса.
- **Dynamic Type**: текст плиток и списка масштабируется; проверять, что на small-плитке текст усекается корректно.
- **RTL**: зеркалится сетка, пейджер и jump-list.

## 10. MVP и что отрезать

**Входит:**

1. Пейджер трёх страниц (ядро Pivot).
2. Сетка: 4 размера, явные ячейки с дырами и выталкиванием вниз (E14; в MVP — жадная упаковка), кастомный layout.
3. Edit-режим: желе, unpin, resize, drag-перестановка.
4. Live-флип для простых текстовых плиток + бейджи + стахгер + паузы.
5. Список приложений с буквами + секция настроек, двусторонний pin/unpin.
6. Левая страница-хук.
7. Обои + параллакс.
8. SwiftUI-фасад, VoiceOver + Reduce Motion, персистентность TileStore.

**Отрезано в v1:** фото-слайдшоу в плитках, push-обновления контента, «идеальная» упаковка без дыр (дыры теперь настоящие, §3), peek-анимация, автоподбор числа колонок под размер экрана (число колонок задаёт хост, по умолчанию 6 — D26), deep-links из плиток.

## 11. Риски

- **Drag-перестановка на переменной сетке** — главный источник багов; закладывать тесты на случайных конфигурациях плиток.
- **Жестовый стек** — самый сложный в проекте: горизонтальный пейджер × вертикальная сетка × вертикальный список × системный жест слева. Разруливается правилом доминирующей оси + политикой «корневой экран».
- **Флипы vs скролл** — джиттер при неаккуратной реализации; лечится только трансформами и паузами.
- **Культурный риск**: живой рабочий стол — самая «чужая» для iOS вещь из всех трёх компонентов; только как опциональный режим, не как дефолтная навигация.

## 12. Структура проекта: общий Core

У трёх компонентов накопился общий слой: инвариант `t`, пейджер с `pagingEnabled`, арбитраж жестов (вариант B), правило «никакого layout в скролле», SwiftUI-фасад. Предлагаемая структура (детали и контракты — в **CORE-IOS-DESIGN.md**):

```
TesseraKit (SPM-пакет)
├── TesseraCore        ← пейджер, параллакс, арбитраж жестов, фасады
├── TesseraPanorama    (свой снап, peek, фон)
├── TesseraPivot       (лента заголовков, индикатор)
└── TesseraStartScreen (сетка плиток, live-движок, 3 страницы)
```

## 13. Итог

Рабочий стол — композиция уже спроектированных механик (пейджер Pivot, параллакс Panorama, вариант B для вертикали) плюс два по-настоящему новых «монстра»: плиточная сетка с переменными размерами и live-движок. Сложность концентрируется в трёх точках: размещение по ячейкам с выталкиванием вниз (в MVP — жадная упаковка), drag-перестановка с анимацией «расступания» и дисциплина флипов (только трансформы, стахгер, паузы). Если эти три точки выдержать, остальное собирается из уже готовых деталей.

## 14. Уточнения MVP (29.10.2026)

Решения пользователя, уточняющие этот документ перед реализацией (полные формулировки — D12–D15
в [STATE.md](STATE.md)):

1. **Рабочий стол — ярлыки и папки.** Компонент выглядит как рабочий стол с ярлыками и папками;
   ярлык — **просто действие**: `id`, `title`, `icon`, `action: () -> Void`, опциональный `badge`

   не используется.
2. **Обе боковые страницы опциональны.** Левая (хук, `QuickPanelProviding`) и правая (список
   приложений/настроек) существуют, только если хост их задал; пейджер масштабируется от 1
   страницы (только START) до 3.
3. **Папки — через функцию одобрения.** Создание папки, добавление ярлыка в папку и перемещение
   между папками разрешает колбэк хоста (дефолт — разрешено).
4. **Live-плитки закладываются** (флипы, стахгер, паузы, Reduce Motion — §4 без изменений);
   размеры ярлыков — **4 вида**: 1×1, 2×2, 4×2, 4×4.

## Отступления реализации (v0.1, 29.10.2026)

> Сверка проектного документа с фактическим кодом релиза 0.1.0. Текст выше не переписывался: отступления зафиксированы отдельной секцией. Формат пункта: что обещал документ → что делает код → решение.

1. **§5 «Режим редактирования»: кто его подключает.** Документ (и схема §2) обещал, что редактирование — часть экрана: `TileEditCoordinator` внутри `StartScreenViewController`, long-press входит в режим «желе». Код: `TesseraStartScreenViewController` и `StartScreenView` координатор не создают и собственного API входа в редактирование не имеют — наружу открыта только сетка (`gridView`) как точка подключения координатора. Хост сам создаёт `TileStore` и `TesseraTileEditCoordinator(grid:store:configuration:)`, передавая сетку экрана (`public var gridView` контроллера), а координатор в инициализаторе сам вешает на неё long-press (0.45 с) и tap по фону; дальше хост вызывает `beginEditing()`, `endEditing()`, `toggleEditing()` тогда, когда считает нужным. Решение: в v0.1 режим редактирования — хост-опция поверх готовой сетки; владение координатором экраном отложено (так приложение, которому редактирование не нужно, не платит за координатор и его оверлеи).

2. **§2/§6 «Страница справа» и принадлежность `TileStore`.** Документ обещал: `AppsListPage` — часть экрана, `TileStore` — компонент экрана (схема §2), настройки — «секция/элемент списка». Код: правая страница — произвольная фабрика `() -> UIViewController` (решение D13); `TesseraAppsListPageViewController` — опциональный готовый класс (`make(store:settings:texts:)`), который хост может не использовать вовсе. Экран данных не хранит: `TesseraStartScreenViewController.configure(leftPanel:rightPage:)` и `StartScreenView.init(snapshot:style:leftPanel:rightPage:...)` принимают готовый снимок сетки (`TileGridSnapshot` через `reload(grid:)` в UIKit и `snapshot:` в SwiftUI), `TileStore` не создаётся и не удерживается. Настройки — строки хоста (`TesseraAppsListSettingsItem` с `id`/`title`/`subtitle`/`icon`/`action`), компонент не знает их смысла. Решение: `TileStore` живёт у хоста (единственный писатель), экран — презентационный слой; схему §2 читать как предлагаемую компоновку приложения, а не как состав библиотеки.

3. **§2 «Модель»: фактический состав `StartScreenDelegate`.** Документ обещал события «тап, pin/unpin, переходы страниц, хук». Код: в протоколе четыре события — `startScreen(_:didTapShortcut:)`, `startScreen(_:didTapFolder:)`, `startScreen(_:didChangePage:index:)`, `startScreen(_:didChangeHookVisibility:)`, все с пустыми реализациями по умолчанию (обязательных нет). Pin/unpin в делегате отсутствует: закрепление — операция модели (`TileStore.pin`/`unpin`, в том числе из опциональной страницы списка), а режим редактирования сообщает об откреплении через `TesseraTileEditCoordinatorDelegate` (`tileEditCoordinator(_:didUnpin:)` и соседние события resize/move/папок). Тап по ярлыку — событие, а не вызов `TileDescriptor.action` (D12): действие выполняет хост. Решение: актуальный контракт — четыре события выше; pin/unpin и редактирование — в `TesseraTileEditCoordinatorDelegate`; перечисление §2 оставлено как проектное намерение.

4. **§2/§3 «Модель раскладки»: где живут координаты.** *[заменено E14: позиция теперь — явная ячейка `row`/`column`, координаты персистятся (D30, п. 49–52)]* Документ обещал: «Позиция хранится в юнитных координатах». Код: `TileStore` хранит только порядок элементов сетки (`gridOrder`), авторитетные размеры (`sizes`, размер папки в `FolderRecord`) и папки; `TileGridSnapshot.layoutItems` — пары «id + размер» в порядке сетки, без колонок и строк. Юнитные координаты вычисляются заново при каждой раскладке: `TesseraTileCollectionViewLayout` вызывает `TileLayoutEngine.unit(screenWidth:columns:gaps:)`, затем `TileLayoutEngine.pack(items:columns:unit:)` и `TileLayoutEngine.rect(for:unit:gap:origin:)`. То есть колонка/строка — производные от порядка, размеров и доступной ширины. Решение: координаты не персистятся — именно это делает поворот/iPad бесплатными; §3 в этой части трактуем как описание вычисляемой раскладки, а не формата хранения.

5. **§3 «Плиточная сетка»: «честные дыры» отменены — финальная раскладка строго компактная (E8.5).** *[заменено E14 (D30): строгая компактность отменена, дыры снова настоящие; упаковка по порядку — только запасной путь (п. 49–54)]* Документ обещал жадную упаковку, в которой «дыры допускаются честно»: под wide/large плитками остаются пустые юниты, пока в них не поместится следующая плитка. Код: `TileLayoutEngine.pack` (публичный вход; реализация — `packCompact`) ставит каждую плитку в самую верхнюю-левую позицию, где она помещается целиком, и затем схлопывает раскладку вверх-влево до неподвижной точки (`stabilize`): ни одну плитку нельзя сдвинуть вверх или влево, пустых строк не остаётся. Свободный юнит остаётся только там, куда не помещается ни одна из **текущих** плиток (например, справа от 2×2, если следующая — 4×2); как только появляется плитка подходящего размера, она занимает это место, а после перетаскивания или открепления нижние плитки поднимаются в освободившееся место. Строгая компактность применяется и к обычной раскладке, и к edit/drag-переупаковке (обе идут через `pack`), поэтому визуал режимов не различается; панель раскрытой папки (D17) по-прежнему не упаковывается как плитка — она полноширинная строка под полосой папки (п. 11), а элементы под ней переупаковываются компактно. Решение: §3 в части «честных дыр» не действует — по спеке WP финальная раскладка компактна сверху вниз (PLAN E8.5); отступление зафиксировано здесь. Тесты: `TileLayoutEngineTests` — `assertCompactPacking`, схлопывание и reflow после утаскивания.

6. **§8 «Параллакс фона»: направление и расположение слоя обоев (E10.7б, W1, 30.10.2026).** Документ задавал `backgroundOffset = offset.y × factor` и «обои выше `contentSize`», не уточняя знак на экране и сторону запаса. Код: `TesseraParallaxLayer` (Core) лежит рядом со скроллом сетки, а не внутри него, и проецирует смещение на экран со знаком минус (`transform = −offset × factor`): при прокрутке вниз обои уезжают вверх вместе с плитками, но медленнее (до W1 обои ехали навстречу). Страница START ставит начало слоя на `padding` выше вьюпорта (поле под «резину» над верхом), а весь ход фона (`maximumOffsetY × factor`) и нижнее поле — ниже; вьюпорт закрыт при offset ∈ [−padding/factor, maximumOffsetY + padding/factor]. Решение: формулу §8 читать как смещение в координатах контента, экранная проекция — `−backgroundOffset` (Core, «Отступления реализации», п. 8); направление покрыто тестом `StartWallpaperParallaxTests`.

7. **Модель: индексы операций — видимые (E10.3a/b, W2, 30.10.2026).** *[заменено E14.6: индексного API нет (D33, п. 54)]* Документ не различал «порядок сетки» и «то, что видно на экране». Код до W2: `TileStore.move(_:toIndex:)` и `pin(_:at:)` считали индексы в `gridOrder`, где после сокращения каталога остаются невидимые ключи (ярлыки вне каталога), а drop/превью работают в видимых индексах — плитка вставала не туда, а делегат `didMove` получал неверный индекс. Код после W2: индексы `move`/`pin(at:)` и новых `moveItem(_:toIndex:columns:) -> Int?`, `pinTile(_:at:columns:) -> Int?` — в пространстве видимого снимка; невидимые ключи остаются на своих позициях в `gridOrder`; новые перегрузки возвращают фактический видимый индекс. Решение: публичный контракт индексов `TileStore` — видимые индексы снимка; координатору (W4) — перейти на `moveItem(..., columns:)` и отдавать делегату возвращённый индекс. Тесты: `TileStoreVisibleOrderTests`.

8. **Модель: порядок модели = порядок чтения (E10.15, W2, 30.10.2026).** *[заменено E14: порядок чтения — производное от ячеек, канонизация удалена (п. 54–55)]* Документ считал порядок элементов и визуальный порядок одним и тем же. При строгой компактной упаковке (п. 5) более поздняя плитка может встать выше более ранней (`[medium A, wide W, small S]` читается A, S, W) — drag-индексы и порядок VoiceOver расходились с экраном. Код: после мутаций с известным числом колонок (`resize(_:to:columns:)`, `moveItem`/`pinTile` с `columns`) хранилище канонизирует видимый порядок к порядку чтения (строка, затем колонка слотов `pack`); одно изменение — один `onChange` и одна запись на диск; явный вход — `canonicalizeVisibleOrder(columns:)`, чистая функция — `TileStore.readingOrder(of:columns:)`. Решение: видимый порядок модели совпадает с экранным при известных колонках; хосту/координатору — вызывать `canonicalizeVisibleOrder(columns:)` после операций без колонок (unpin, папки, `setCatalog`, `load`). Следствие строгой компактности: в `[medium A, small S, wide W]` перенос S на место W визуально ничего не меняет. Тесты: `TileStoreVisibleOrderTests`.

9. **Персистентность: нечитаемый файл не затирается (E10.3d, W2, 30.10.2026).** Документ обещал персистентность `TileStore` без политики для повреждённого файла. Код до W2: повреждённый или записанный более новой схемой файл перезаписывался схемой v1 при первом автосохранении. Код после W2: такой файл до любой записи переименовывается в `<имя>.unreadable-<ISO-дата>.json` (при совпадении — суффиксы `-2`, `-3`, …), путь — в `lastUnreadableFileBackupURL`; `load()` по-прежнему бросает ошибку. Решение: данные пользователя не теряются молча; восстановление — забота хоста. Тесты: `TileStoreRecoveryTests`.

10. **Персистентность: чистка папок по каталогу после загрузки (E10.3c, W2, 30.10.2026).** Документ не описывал согласование файла с каталогом. Код: чистка выполняется и в `setCatalog`, и в `load()` — папка без ярлыков каталога распускается, неизвестные ярлыки удаляются из папок; осиротевшие папки из файла (нет в порядке сетки) встают в конец сетки. Решение: после загрузки в модели нет «мёртвых» папок и невидимых ключей внутри папок. Тесты: `TileStoreRecoveryTests`.

11. **Раскладка: панель папки — под «полосой папки» (E10.1, W2, 30.10.2026).** D17 обещал панель «под плиткой папки». Код до W2 решал «выше/ниже панели» по началу строки плитки (`slot.row < folderEndRow`): плитка, начинающаяся в строках папки и заканчивающаяся ниже, оставалась на месте и перекрывалась панелью. Код после W2: `TileLayoutEngine.folderBandEndRow(for:in:)` расширяет нижнюю границу строк папки до `max(row + unitRows)` всех пересекающих её плиток (итеративно) — это «полоса папки»; панель встаёт под полосой, плитки полосы и выше остаются на месте, плитки ниже переупаковываются компактно от `panelTop + panelHeight + itemSpacing`. Вход для индекса вставки — новая перегрузка `folderPanelInsertionIndex(items:columns:expandedFolderID:)` (старая — устаревший вход без полосы); `rowsBelowOffset` возвращает `panelHeight + spacing` (новый параметр `spacing`, по умолчанию 8). Решение: D17 уточнён в `STATE.md` («полоса папки»). Тесты: `FolderBandLayoutTests`, `FolderPanelInsertionTests` («ступенька» `[папка 2×2, small, small, ярлык 2×2]`).

12. **Раскладка: пиксельное выравнивание юнита (E10.1, W2, 30.10.2026).** Документ (§3) задавал юнит как `(ширина − зазоры) / колонки` без учёта пикселей — рамки плиток ложились на дробные пиксели. Код: `TileLayoutEngine.unit(screenWidth:columns:gaps:scale:)` округляет юнит вниз до `1/scale`, зазор — к ближайшему пикселю; остаток ширины делится на поля (левое — `floor(остаток/2)`, правое — остальное), сетка центрируется (`gridMetrics`). Масштаб — `traitCollection.displayScale` (fallback `UIScreen.main.scale`; `0` — без выравнивания); прежняя `unit(screenWidth:columns:gaps:)` не изменилась. Остаток снят в W3 (E10.4): `magnetSlotCenters(for:)` считает геометрию через `gridMetrics` и совпадает с рамками раскладки до пикселя (см. п. 23). Тесты: `TileGridPixelAlignmentTests`, `TileGridSnapshotApplicationTests`.

13. **Раскладка: зазор панели папки = `itemSpacing` (E10.1, W2, 30.10.2026).** Код до W2 ставил зазор между панелью и соседними плитками жёстко 8 pt. Код после W2: зазор берётся из `itemSpacing` сетки (через `gridMetrics`), высота — `panelHeight(for:width:columns:spacing:scale:)`; внутренние поля панели (12 pt) и зазор «заголовок — сетка» (8 pt) остались константами. Решение: панель следует ритму сетки при любом `itemSpacing`; внутренние отступы панели — часть её стиля.

14. **§1/§2 «Три страницы»: синхронизация с пейджером и источник `currentPage` (E10.6, T1, 02.11.2026).** Документ не уточнял, кто владеет текущей страницей при пересборке набора и программном переходе. Код: после любой пересборки страниц (`configure(leftPanel:rightPage:)`, смена политики края, «заморозка» хука) контроллер явно ставит пейджер на фактический индекс подтверждённой страницы (`go(toPage:animated: false)`), а незавершённый программный переход отменяется. `currentPage` записывается только по подтверждению пейджера (`didShowPageAt`): анимированный `showPage` не меняет его до завершения, перехват пальцем оставляет страницу, на которой пейджер остановился. Идентификаторы хука и правой страницы содержат поколение: новый поставщик или фабрика в `configure` пересоздают страницу — пейджер Core после W1 переиспользует контроллеры с тем же `id`. Решение: источник истины — Core; известный остаток — если палец вернул пейджер на исходную страницу во время анимации к хуку при политике края, хук остаётся в свайпе до следующего перехода (Core не сообщает о переходе без смены страницы). Тесты: `StartScreenControllerReviewTests`.

15. **§7 «Страница слева: хук» и §2 `StartScreenDelegate`: колбэки, UIKit-делегат, анонсы (E10.6, E10.8, T1, 02.11.2026).** Документ обещал «колбэки появления/скрытия» без уточнения момента. Код: `quickPanelWillAppear` приходит, как только хук начинает появляться — при свайпе (по прогрессу пейджера, `|t − индекс хука| < 1`), при программном показе до начала перехода, при появлении экрана с открытым хуком (`viewWillAppear`). `quickPanelDidDisappear` приходит, когда хук полностью ушёл или экран скрыт (`viewDidDisappear`), и всегда тому же экземпляру, что получил `willAppear`: при замене или удалении поставщика на экране прежний получает `didDisappear`, новый — `willAppear`. До показа экрана (в том числе из `viewDidLoad`) колбэков, событий и анонсов нет; стартовая страница не озвучивается. У контроллера появился UIKit-`delegate: StartScreenDelegate?` (weak) — `didChangePage` по подтверждению пейджера, `didChangeHookVisibility` по тем же переходам, что колбэки хука. Тапы по-прежнему идут через `gridView.onTap`. `StartScreenView` не перехватывает делегата пейджера: его координатор — UIKit-делегат контроллера. Решение: п. 3 дополняется — UIKit-хосты получают события страниц через `delegate` контроллера. Тесты: `StartScreenControllerReviewTests`, `StartScreenViewFacadeTests`.

16. **§1 «Арбитраж» против анимации папки (D17) и §4 «Паузы» (E10.6, T1, 02.11.2026).** Документ обещал блокировку вертикальных детей на время горизонтального жеста и паузу плиток вне экрана. Код: сетка START блокируется не через `isScrollEnabled` (его со своими снимками пишут анимация панели папки и координатор редактирования — снимок арбитра поверх них мог навсегда оставить сетку выключенной), а выключением её `panGestureRecognizer`, который контроллер включает обратно, только если выключил сам. Скроллы боковых страниц блокирует `TesseraGestureArbiter`, как раньше. Live-плитки и превью папок START стоят на паузе, пока START-страница не показана пейджером (appearance только текущей странице, Core «Отступления реализации», п. 7); пауза переприменяется после раскладки. 30. **§5 «Перетаскивание»: зоны плитки-папки, центр без удержания, магнит от центра снимка, строгие границы E8.6, «желе» ±1,2° (E10.5-A, E9.5, E9.8а, W4, 02.11.2026).** Документ описывал drag как «снимок едет за пальцем, соседи расступаются», но не фиксировал: поведение плитки-папки как цели, точку отсчёта магнитизма, семантику drop в центр без удержания, амплитуду «желе» и точность границ E8.6. Код до W4: у плитки-папки была только зона add-to-folder (переставить ярлык на место папки было нельзя — drop на папку всегда добавлял внутрь); магнит (`TesseraTileMagnet`) считал расстояние по точке **пальца**, а снимок ставился в центр слота — плитка, взятая не за центр, прыгала до половины плитки; после смещения пальца за допуск удержание E8.6 не перевзводилось до выхода из зоны/смены цели; drop в центр ярлыка без удержания мог зафиксировать **предыдущее** превью перестановки; «желе» фактически было ±1,2° (спека §5 — ±2°). Код после W4: (а) у плитки-папки есть краевые зоны: левая/правая половины (вне центральной зоны) — `.reorder` с базовым индексом папки, центральная зона — add-to-folder только после удержания E8.6 (D14), папка-источник в папку не таскается; (б) магнит считает расстояние от **центра снимка** (`point + grabOffset`), поэтому снимок смещается к центру слота не больше чем на радиус притяжения, а стартовая зона/над-панелью/Reduce Motion остаются как были; (в) после отмены удержания (смещение на допуск или больше) возврат пальца в допуск запускает **новый** отсчёт 600 мс; (г) drop в центр без удержания — возврат на исходное место (no-op), push-превью для центральной зоны не делается; (д) при входе в edit и старте drag раскрытая панель папки закрывается штатным `closeFolder`, drag с ячеек панели (`.folderContent`) не начинается; (е) границы E8.6 строгие: смещение **меньше** 10 pt и удержание **больше** 600 мс. Решение E9.5: семантика «центр без удержания = no-op/отмена» зафиксирована в документации и комментариях E8.6; E9.8а: «желе» остаётся базово ±1,2° (на плитку — коэффициент 0,85–1,15), на ±2° не переходим; границы читаются строго. Уточнение m7 (фикс-раунд W4): no-op-семантика E9.5 относится к центру **ярлыка** (и к центральной зоне плитки-папки, где без удержания drop — тоже возврат на место); панель раскрытой папки — не drop-цель: над `.folderContent` цель `.none`, и drop по ней возвращает ярлык на исходное место. Подсветка «впитывания» сохраняет акцент цели (n5): у центра ярлыка — оранжевый, у центра папки — синий (`.merge`/`.mergeFolder`), отличаются толщина рамки и заливка. При старте drag из long-press раскрытая панель закрывается **мгновенно** (`closeFolder(animated: false)`), чтобы первые кадры drag не шли поверх сдвигающейся раскладки; публичный `beginEditing()` без drag закрывает её анимированно (m3). Тесты: `DragSessionTests`, `TileMergeHoverTests`.

31. **§5 «Перетаскивание»: состояние drag — внешние изменения, deinit/fly-out, двойной unpin, конфигурация на лету, «желе»/дим после reload, `.layoutChanged` (E10.5-B, W4, 02.11.2026).** Документ не описывал гонки состояния drag. Код до W4: внешний `grid.update` во время drag оставлял превью посчитанным от устаревшего `baseSnapshot`, а отмена/`restore` могли откатить сетку к базе и рассинхронизировать её с `TileStore`; `deinit` восстанавливал `autosaves`, но не возвращал скрытую ячейку и не включал `isScrollEnabled`, а fly-out при уже исчезнувшем координаторе оставлял ячейку скрытой; двойной быстрый unpin запускал второй fly-out; смена `controlDiameter` на лету не пересоздавала кнопки (они создаются с диаметром в инициализаторе); после `reloadData` при unpin/создании папки плитки могли замирать без «желе» и терять дим; `.layoutChanged` после unpin/resize не публиковался. Код после W4: (а) модель и применённый снимок сетки сверяются с базой drag — расхождение (внешняя мутация модели или чужой `grid.update`) безопасно отменяет drag, возвращает скрытую ячейку/прокрутку и синхронизирует сетку с **текущим** снимком store (а не с устаревшей базой), внешняя мутация сохраняется; (б) `deinit` и завершение fly-out при уже исчезнувшем координаторе возвращают скрытую ячейку, `isScrollEnabled`, `autosaves`, снимают оверлеи, пустышку, spring и таймеры; (в) unpin получил in-flight guard по tileID: один fly-out, одна мутация, один колбэк; (г) смена конфигурации на лету пересоздаёт контролы, перезапускает «желе» и снимает удержание/магнит; (д) после `render` (unpin, создание папки) «желе» и дим переприменяются к видимым ячейкам; (е) `.layoutChanged` публикуется после unpin/resize/move на следующий проход runloop с ячейкой-фокусом (для unpin — элемент, вставший на место удалённого). M1 (фикс-раунд W4): отложенный сеткой снимок (drag-превью во время анимированного закрытия панели папки, E10.2) при отмене/no-op/`endEditing` заменяется снимком модели даже при совпадающем видимом порядке — `grid.update` перезаписывает pending по last-wins; иначе после завершения перехода сетка применила бы устаревшее превью и разошлась бы с `TileStore`. m3 (фикс-раунд W4): при старте drag из long-press панель закрывается мгновенно, публичный `beginEditing()` — анимированно. Контракт `startDrag` (m2): к моменту захвата снимок сетки обязан совпадать с моделью, иначе drag не начинается (в DEBUG — assertion); долгое нажатие при рассинхронизации не начинает перетаскивание, хосту нужно применять store-снимки. Решение: владелец дима и доступности прокрутки остаётся у сетки (пп. 22, 24), координатор отвечает за восстановление после своей сессии. Тесты: `DragSessionTests`.

32. **§5/§6/§14 «Порядок и папки»: фактический индекс drop, канонизация, экран папки через `onTap` (E10.5-C, W4, 02.11.2026).** *[заменено E14.5/E14.6: drop идёт по ячейкам, делегат получает ячейку, канонизации нет (п. 53–54)]* Документ обещал, что порядок хранит `TileStore` (§6), а тап по ярлыку в папке вызывает действие (D17). Код до W4: drop и публичный `move` писали `TileStore.move(_:toIndex:)` без числа колонок и отдавали делегату запрошенный индекс, а не фактический (зажатый/канонизированный); встроенный экран папки вызывал `TileDescriptor.action` напрямую в обход `onTap`/делегата хоста. Код после W4: drop и публичный `move` идут через `TileStore.moveItem(_:toIndex:columns:)` (E10.3a), делегат получает **фактический** индекс из хранилища, после drop сетка синхронизируется со снимком store (включая канонизацию порядка E10.15); признак «порядок изменился» для `move` вычисляется **до** мутации (m1, фикс-раунд W4): хост, синхронно применяющий `store.onChange` к сетке, всё равно получает `didMove` и `.layoutChanged`; после unpin и папочных операций вызывается `TileStore.canonicalizeVisibleOrder(columns:)`; тап по ярлыку на экране папки идёт общим маршрутом `grid.onTap` (событие обрабатывает хост один раз, действие выполняет хост — D12), в режиме редактирования не активируется. m4 (фикс-раунд W4): активация выполняется в completion закрытия sheet (как раньше `action`), а не до dismiss, чтобы событие хоста не конфликтовало с уходом экрана; если координатора/сетки уже нет, действие ярлыка выполняется напрямую (fallback). **Breaking для интеграторов:** если хост полагался на прямой вызов `action` из экрана папки, теперь действие нужно обрабатывать по `grid.onTap` (как для плитки сетки; ср. п. 28 для панели раскрытой папки). Активация ярлыка в папке из режима редактирования не выполняется. Тесты: `DragSessionTests`.

33. **§1–§4 «Строки интерфейса по умолчанию»: внутренний источник — SPM-ресурсы en/ru с dotted-ключами (E9.8г, W5, 02.11.2026).** Документ не фиксировал, на каком языке и откуда берутся строки, которые компонент показывает по умолчанию, и что именно из них локализуется. Код до W5: user-facing строки жили литералами прямо в Swift-коде (часть — по-русски, часть — по-английски), локализация таргета не поддерживалась. Код после W5: строки вынесены в ресурсы таргета — `Localizable.strings` в `en.lproj` и `ru.lproj` (объявлены как `resources` в `Package.swift`), по **41 ключу** в каждой таблице; паритет ключей en/ru проверяется тестом. Ключи — стабильные dotted-идентификаторы (`a11y.editing.entered`, `folderScreen.done`, `appsList.pinActionTitle`, `panel.expanded`, …), переводятся только значения. Резолв — через `Bundle.module` (внутренний `TesseraStartScreenStrings`; `@usableFromInline` помечены сам `enum` и его члены, нужные default-аргументам публичного `TesseraAppsListTexts.init`; публичная поверхность модуля не менялась). Ресурсный бандл `TesseraKit_TesseraStartScreen.bundle` — часть пакета: если потребитель скопировал модуль без него, обращение к строке падает с `fatalError` (требование к интеграторам). Локализованный объём — user-facing строки: 34 обращения в `TileEditCoordinator` (VoiceOver-озвучивания, меню/алерты/экран папки, custom actions, названия размеров), 5 дефолтов `TesseraAppsListTexts`, accessibility value «раскрыта» панели в `TileGridView`. **Не в таблицах** — остаются английскими дефолтами/параметрами хоста: `startPageTitle`/`quickPanelTitle`/`applicationsPageTitle` контроллера и `StartScreenStyle` (подписи страниц START/хука/списка), а также тексты, переданные хостом (`TesseraAppsListTexts`, `folderTitle` и т.п.), — они перекрывают значения по умолчанию, но только те строки, которые параметр принимает. При локали устройства, отличной от en/ru, действует fallback — английский (неподдерживаемая локаль не даёт пустую строку или технический ключ). Плюрализация: обычные `.strings` не поддерживают plural-варианты, поэтому словоформы «ярлык» лежат отдельными ключами (`folderScreen.tiles.word.one/few/many`), а правило выбора — в коде (`en` — одна/множественная, `ru` — одна/несколько/много с учётом 11–14); для нового языка нужны свои правила в коде или переход на `.stringsdict`. Диагностика для разработчика (ошибки `TileStore`, `precondition`/`fatalError`, deprecation-сообщение, DEBUG-assertion) намеренно остаётся русскими литералами вне UI-таблиц (allowlist из 8 литералов в `LocalizationTests`). Решение: источник UI-строк — SPM-ресурсы en/ru с dotted-ключами и fallback на английский; публичный API не менялся. Хост-параметры перекрывают только строки, которые принимают; внутренние VoiceOver-строки и строки экрана папки хостом не переопределяются — для нового языка нужны таблицы en/ru и правила плюрализации (или `.stringsdict`).

34. **§5 «Перетаскивание»: трактовка push-физики E8.4 (E8.4, E9.11, W5, 02.11.2026).** *[заменено E14.5: превью строится по ячейкам (`TileLayoutEngine.inserting`), `previewOrder` удалён (п. 53–54)]* Документ (E8.4): «плитка-цель и всё ниже неё плавно сдвигаются вниз на высоту перетаскиваемой». Код: во время drag модель не меняется; порядок соседей — превью `TileLayoutEngine.previewOrder`, применяемое в сетку снимком (`grid.update`); перетаскиваемая встаёт в слот цели, а цель и плитки ниже переупаковываются строго компактно (п. 5) — освободившееся место может подтягивать часть плиток вверх. То есть это push-эффект через перестановку и переупаковку, а не сдвиг на фиксированную высоту: запись порядка в `TileStore` происходит один раз на drop, отмена возвращает снимок на момент захвата. Решение: E8.4 читать как «push-эффект через preview-порядок»; отдельной анимации сдвига на высоту перетаскиваемой нет.

## Отступления реализации (E11, 02.11.2026)

35. **§5/§14 «Папки: размер новой папки, вынос из папки, цель полёта снимка» (E11.2–E11.4, 02.11.2026).** (а) E11.4 **(отменено E12.2, см. п. 41)**: `TileStore.createFolder` больше не ставил `.medium`, а наследовал актуальный размер ярлыка-цели (сохранённый в `sizes` либо из дескриптора): папка занимает его слот, соседи не переупаковываются. Кламп по числу колонок не нужен — ярлык уже помещался в сетку с этим размером, слот не меняется; схема персистентности не менялась (размер папки хранится в её записи, как и раньше). (б) E11.2: ярлык, вынесенный из папки на рабочий стол (`moveBetweenFolders(_:to: nil)`), встаёт не в конец сетки, а сразу после папки-источника; если папка распалась (вынесен последний ярлык), ярлык занимает её место. Публичный API расширен аддитивно: `TileStore.moveBetweenFolders(_:to:at:)` и такой же метод координатора принимают необязательный индекс в пространстве видимого снимка (как `moveItem`, значение зажимается); прежние сигнатуры сохранены. Порядок чтения под число колонок по-прежнему приводит `canonicalizeVisibleOrder`/координатор, фокус VoiceOver — на вынесенном ярлыке. Делегат `didMove(toFolder:)` индекс не получает (аддитивный вариант с индексом — п. 36). (в) E11.3: в `dropIntoNewFolder` рамка новой папки читается после канонизации и `render(animated:)`, поэтому снимок схлопывается в плитку-папку, а не в слот плейсхолдера; рамка цели доступна тестам через внутренний `lastCollapseTargetFrame`.

36. **§5 «Папки: ярлык из панели в режиме редактирования» (E11.1, 02.11.2026).** Документ и код до E11 не давали вытащить ярлык из папки перетаскиванием: `beginEditing` закрывал панель, тап по папке в edit раскрытия не запускал, долгое нажатие по панели только входило в edit. Решение (вариант A): (а) тап по папке в edit открывает нативную панель D17 и режим не прерывает — `handleItemTap` ведёт себя одинаково в обоих режимах: `folderTapHandler` вызывается и в edit (`true` отменяет раскрытие и `onTap`), иначе приходит `onTap` и панель переключается; `beginEditing()` по-прежнему закрывает уже открытую панель. (б) долгое нажатие по иконке панели в edit мгновенно закрывает панель (`closeFolder(animated: false)`, как в m3) и поднимает ярлык: источник drag — папка (`TesseraTileDragSession.sourceFolderID`), снимок иконки берётся до закрытия, смещение захвата считается от рамки иконки. Модель за время drag не меняется: сетка показывает **отображаемый** снимок — ярлык вынут из состава папки и вставлен отдельным ярлыком сразу после неё (его слот/пустышку и push-превью `TileLayoutEngine.previewOrder` обслуживает обычная машина E8.4); сверка с моделью (`modelMatchesBase`) идёт по реальному снимку (`modelBaseSnapshot`). (в) цели: сетка/пустое место — вынос на позицию превью `TileStore.moveBetweenFolders(_:to: nil, at:)` (индекс уменьшается на единицу, если папка из одного ярлыка распадается и стояла перед ярлыком), порядок читается под число колонок, фокус VoiceOver — на ярлыке; центр **другой** папки с удержанием E8.6 — `moveBetweenFolders(_:to: folder)`; без удержания — no-op; центр обычного ярлыка для такого источника папку **не создаёт** (двухшаговое создание требует ярлыка на сетке) и работает как перестановка; центр родной папки, панель, отмена и отказ одобрения хоста — возврат ярлыка в папку без изменения модели (снимок «впитывается» в рамку папки). Если вынесен последний ярлык, папка распадается (поведение `TileStore`). Перестановка внутри папки — вне объёма. (г) Делегат: добавлен `didMove(_:toFolder:atIndex:)` с фактическим индексом при выносе (`nil` — при переносе в папку); координатор вызывает **только его**, реализация по умолчанию пересылает событие в прежний `didMove(_:toFolder:)`, поэтому прежние делегаты продолжают получать событие, а новые — индекс (ровно один из двух). Протокольная реализация по умолчанию именно пересылающая, а не пустая: иначе координатор не знал бы, какой из двух колбэков реализован делегатом. Новая строка локализации — причина отказа переноса (`a11y.grouping.reason.moveDenied`, en/ru). Reduce Motion, haptics и озвучивание — как у остальных папочных drop'ов.

37. **§9 «Accessibility»/§5 «Папки»: custom actions папок и атомарное создание папки (E11.5, E11.6, 02.11.2026).** (а) E11.5: в режиме редактирования ячейка ярлыка на сетке получает к «Открепить»/«Изменить размер» пункты «Добавить в папку <название>» — по одному на существующую папку, не больше `TesseraTileEditCoordinator.maxFolderActions` (6, первые папки в порядке сетки; пустое название заменяется `folderTitle` конфигурации, затем общей подписью папки). Ярлыки панели раскрытой папки получают «Убрать из папки» (вынос сразу после папки через `moveBetweenFolders(_:to: nil)`) и «Переместить в папку <название>» по одному на другую папку (тот же кап). Все пункты вызывают публичные `addToFolder`/`moveBetweenFolders` координатора, то есть проходят функцию одобрения хоста (D14), озвучивание и фокус; отказ возвращает `false` и даёт `didFailGrouping`. У плитки-папки новых действий нет. Сверка действий идёт по подписи (плитка + состав папок), поэтому новая папка появляется в уже настроенных ячейках; ярлыки панели получают действия отложенной сверкой (внутренний шов сетки `panelShortcutsDidConfigure`), выход из edit снимает всё. «Создать папку с…» **не реализовано**: нужен выбор второго ярлыка (picker), для VoiceOver это отдельный UI вне простого объёма; создать папку без drag можно публичным `createFolder(withTile:)`. Строки: `a11y.action.addToFolderFormat`, `a11y.action.removeFromFolder`, `a11y.action.moveToFolderFormat` (en/ru). (б) E11.6: создание папки drop'ом (два одобряемых шага D14) атомарно: внутренний `TileStore.createFolder(withTile:adding:title:)` применяет первый шаг только в памяти, спрашивает хост о втором и при отказе возвращает слот цели и убирает запись папки — без `onChange`, автосохранения и `objectWillChange` для промежуточного состояния и отката; при успехе уведомление одно. Хост по-прежнему видит оба одобрения (`.createFolder`, затем `.addToFolder`; при втором одобрении папка уже содержит целевой ярлык). Координатор шлёт `didCreateFolder` только после успеха обоих шагов, непосредственно перед `didAdd`; при отказе второго шага делегат получает только `didFailGrouping(.addToFolder, …, folderID: nil)` (папки не существовало), модель — ровно как до drop'а. Текст причины `a11y.grouping.reason.tileAddDenied` изменён на «добавление ярлыка в новую папку запрещено». Публичный API не менялся (новый метод хранилища internal).

38. **§5 «Drag: цель определяется по базовой раскладке» (E11.7, 02.11.2026).** Документ не уточнял, по каким рамкам ищется цель под пальцем; код искал элемент и считал центр (25%) по рамкам сетки, уже сдвинутым push-превью. Подтверждено оконным тестом: плитка/папка, уехавшая из-под пальца, оставляла палец над пустышкой (`.none`), поэтому зона центра (группировка/добавление в папку, E8.6) была недостижима при подходе в сторону сдвига, а `.group`/`.folder` срабатывали по кадрам, которых пользователь не видел. Решение: `updateHoverTargets` решает цель по **базовой** раскладке — раскладке `session.baseSnapshot.items` (тот же порядок, что у `.reorder`/`baseIndex`); рамки считает `TesseraTileGridView.baseContentFrames(for:)` той же геометрией, что `TesseraTileCollectionViewLayout` (пиксельные края, `gridMetrics`, `pack` по ужатым размерам, RTL), в координатах контента и кэшируются в сессии; кэш перестраивается при смене ключа геометрии (размер, колонки, поля, зазор, масштаб, направление), а `contentOffset` учитывается на каждом шаге переводом в координаты сетки (кадры автопрокрутки видят актуальное смещение). Над собственным базовым слотом перетаскиваемого элемента цель — `.none` (превью остаётся прежним, поведение «c»). Подсветка цели рисуется по-прежнему на видимой (сдвинутой) рамке. Пока папка раскрыта (в т. ч. во время анимированного закрытия панели) раскладка сетки не совпадает с базовой, и действует прежний хит-тест по рамкам сетки; drag из панели (E11.1) работает по базе с синтетическим ярлыком. Гистерезис зон не вводился. Покрыто `DragSessionTests` (репро с папкой, граница центра, `contentOffset`).

39. **§5 «Drag ярлыка из панели: раскладка во время drag» (E12.1, 02.11.2026).** *[уточнено E14.5: после E14 «дыра» модели — настоящая ячейка, превью считается от базы (п. 53)]* Сообщение «ярлык вынесен в дыру и попал в соседнюю папку» не воспроизведено ни в 4, ни в 5/6 колонках, поведение не менялось. Фиксируем свойство, на которое легко ошибиться при ручной проверке: во время drag из панели сетка показывает отображаемый снимок (папка-источник без ярлыка плюс синтетический ярлык после неё), поэтому упаковка отличается от модельной — «дыра» модели занята другой плиткой, а соседние плитки могут оказаться вплотную к ней. Цель по-прежнему выбирается по точке пальца на базовой раскладке (E11.7), а не по центру снимка: при крайнем хвате иконки панели палец может стоять над центром другой папки, пока снимок (магнит) выглядит в пустой клетке. Удержание над другой целью сбрасывается при уходе пальца (покрыто тестами `DragSessionTests`, E12.1).

40. **§5 «Удержание E8.6: якорь переносится при смещении» (E12.3/E12.1, 03.11.2026; меняет E8.6/E9.8а/E10.5-A3).** Гипотеза «снимок с магнитом расходится с пальцем» не подтвердилась: притяжение E8.9 выключено над целями `.folder`/`.group`, поэтому у центра другой папки снимок стоит под пальцем при любом хвате иконки панели (радиус 28 pt, хват за центр и углы; E12.1 с краевым хватом в 4/5/6 колонках в соседнюю папку не попадает). Причина несрабатывания слияния — контракт трекера: якорь допуска (10 pt) ставился на первой точке центральной зоны цели, после смещения на допуск или больше трекер уходил в `cancelled` и перевзводился только при возврате к **старому** якорю (E10.5-A3). Палец, идущий к центру несколькими шагами и остановившийся, слияния не получал (то же у drag с сетки), а drop по `.folder` без готовности оставлял только то, что дало push-превью. Решение пользователя: удержание — «палец остаётся в пределах допуска (<10 pt) дольше порога (>600 мс), **считая от последнего заметного движения**». Смещение от якоря на допуск или больше отменяет прежнее удержание (в т. ч. уже выдержанное, подсветка «впитывания» откатывается) и сразу начинает новое: якорь переносится в текущую точку, отсчёт 600 мс идёт заново (`armed`), таймер координатора пересоздаётся. Состояние `cancelled` убрано. Остаются без изменений: строгие границы (<10 pt, >600 мс), смена цели — новое удержание, `reset()` — `idle`, уход из зоны сбрасывает удержание, Reduce Motion, haptic/озвучивание — только когда удержание реально выдержано. Следствия: постоянное движение (каждый шаг ≥10 pt) готовности не даёт; возврат к старой точке после смещения — тоже смещение, то есть новый отсчёт. Остаточное превью: drop по `.folder`/`.group` без готовности идёт через `returnAfterNoOpDrop` → `restore()` (сетка синхронизируется с моделью), и оконный тест `testNotReadyDropOnFolderCenterLeavesNoPushPreview` подтверждает порядок сетки = модели после такого drop'а — отдельный дефект кодом не воспроизведён; наблюдавшееся в ручном прогоне, вероятно, было следствием несработавшего слияния (ярлык возвращается на слот анимированно) и не менялось. Покрыто `TileMergeHoverTests` (якорь, постоянное движение, возврат к старому якорю) и `DragSessionTests` (14-шаговый заход с панели и с сетки, постоянное движение, возврат, слияние с магнитом, краевой хват).

41. **§3/§5 «Папка — всегда medium» (E12.2, 03.11.2026; отменяет E11.4).** Решение пользователя: в Windows 10 Mobile папка всегда средняя плитка 2×2, независимо от размера ярлыка-цели. Поэтому `TileStore.createFolder(withTile:)` и атомарное `createFolder(withTile:adding:title:)` снова создают папку размера `.medium` (константа `TileStore.newFolderSize`); папка из wide/large цели замещает её слот средней плиткой, соседи переупаковываются строго компактно (п. 5), каноничный порядок и рамка полёта снимка (`lastCollapseTargetFrame`, п. 35в) берутся после канонизации и `render`. Схема персистентности не менялась; при загрузке сохранённый размер папки **не нормализуется**: папку можно менять в размере (`resize`/«Изменить размер» работают и для папок, как раньше), поэтому записанный размер — осознанный выбор пользователя, а записи, оставшиеся от короткой жизни E11.4, неотличимы от него; терять размер без ведома пользователя хуже, чем показать один раз папку нестандартного размера. Фраза §3 «размеры плиток 1×1, 2×2, 4×2, 4×4» относится к ярлыкам; новая папка всегда 2×2. Симптом из ручного прогона (слияние на центр wide/large цели с удержанием ~1,5 с не создавало папку) на текущем коде **не воспроизводится**: центральная зона (25%-й отступ от базовой рамки) и `.group` не зависят от размера цели, удержание и `dropIntoNewFolder` — тоже; тест `testMergeOnTargetCenterCreatesMediumFolder` перебирает wide/large/small цели (источник medium/small, до и после цели, 14 шагов и «прыжок») и проходит. Вероятная причина — контракт трекера до E12.3 (п. 40): на большой центральной зоне wide/large палец неизбежно сдвигается больше допуска, и без перевзвода удержание не набиралось; превью «слот под целью» и возврат на старое место — это drop `.group` без готовности (`restore()`), а не отдельный дефект. Проверено на родителе коммита E12.3: 14-шаговый заход на центр цели готовности не даёт.

42. **§5 «Кнопки редактирования: клип и вид» (E12.4/E12.5, 03.11.2026).** Кнопки «открепить»/«размер» были подвью самой сетки, а границами `bounds` обрезалась только коллекция, поэтому у плитки, частично ушедшей под верхний/нижний край, кнопка рисовалась поверх status bar. Теперь кнопки лежат в контейнере `TesseraTileEditControlsHostView` (`clipsToBounds`, рамка = `bounds` сетки, `zPosition` 200, сам касания не перехватывает) и режутся по той же границе, что и плитка; полностью вне `bounds` кнопки скрыты, как раньше. Вид (в духе Windows 10 Mobile): диаметр = ≈ 24 % меньшей стороны плитки, не меньше 20 pt и не больше `controlDiameter` (теперь это потолок: малая плитка ≈ 21 pt, средняя и больше — 28 pt); центр кнопки у угла плитки, выступ за рамку 6 pt по каждой оси (с D48 — 4 pt, п. 60) (зазор плиток по умолчанию 8 pt, поля сетки ≥ 16 pt — на соседей и за край кнопка не заходит; при нулевом зазоре возможно перекрытие кромки соседа); светлая заливка с тёмным символом, кольцо 1 pt и тень — контраст на светлых и тёмных плитках в обеих темах (кольцо — динамический цвет, пересчитывается в `traitCollectionDidChange`). Видимая кнопка мелкая, но зона касания ≥ 44 × 44 pt: `hitTest`/`point(inside:)` оверлея считают попадание по расширенным зонам. Остаточное: на малой плитке кнопка может задеть угол иконки/конец длинной подписи; Reduce Motion, VoiceOver (кнопки не accessibility-элементы, действия — custom actions) и RTL (кнопки зеркалятся) без изменений.
43. **§9 «Dynamic Type заголовков плиток» (E12.6, 03.11.2026).** На accessibility-размерах шрифт подписи плитки (12/14/17 pt × масштаб категории) вырастал до ~30 pt на плитке 73 pt: «Календарь» рвался посреди слова, подписи малых плиток усекались. 45. **§5 «Каноничный порядок модели перед edit/drag» и кнопки без перелёта (E12.10/E12.9, 03.11.2026).** *[заменено E14.5/E14.6: порядок модели не канонизируется, он производное от ячеек; E12.9 (кнопки без перелёта) действует (п. 54)]* Ручной прогон (слияние `Почта → Настройки` одним жестом из обычного режима) дал папку в конце сетки и сдвиг «Работы» вверх. Причина — не база хит-теста (E11.7) и не снимок/render во время `beginEditing`, а **неканоничный порядок модели**: хост (сид Example: `createFolder` без колонок) оставил малую плитку последней в `gridOrder`, упаковка подняла её в «дыру» справа от среднего ярлыка, и видимый порядок разошёлся с порядком модели. Цель и подсветка считаются по базовой раскладке и были верны, но drop работает по слотам модели: `createFolder(withTile:adding:)` заменяет слот цели в `gridOrder` (последний), поэтому папка осталась в конце. Решение: координатор канонизирует порядок (`TileStore.canonicalizeVisibleOrder(columns:)`) на входе в edit (после закрытия панели) и в `handleLongPress` до захвата базы drag'а; если сетка до этого показывала модель, она синхронно подтягивается к ней (`syncGridWithModel` без анимации, `layoutIfNeeded`) — видимая раскладка не меняется, перестановка касается только модели; при расхождении, принесённом хостом, по-прежнему срабатывает m2-проверка на захвате. Документированный контракт «после `setCatalog`/`load()`/операций без колонок хост вызывает канонизацию» остаётся, координатор лишь не полагается на него. Возможно, это же причина E12.1 («дыра» модели занята другой плиткой) — не доказано. Кнопки (E12.9): «влёт из левого верхнего угла» наблюдался при возврате плитки после отпускания long-press'а — оверлей пересоздавался анимированным проходом с нулевой рамкой; теперь он создаётся сразу на месте плитки, а анимация переезда существующих кнопок отключается при Reduce Motion. Покрыто `DragSessionTests` (старт из обычного режима, канонизация без видимых изменений) и `TileEditControlsTests`.

Две причины. (а) Хит-тест E11.7 находит цель только над плитками; над пустым местом (дыра, зазор между плитками, область под плитками) цель была `.none`, и превью оставалось в слоте «сразу после папки» — для drag по сетке то же самое. (б) Раскладка строго компактная (§3, E8.5): ярлык, помещающийся в дыру, упаковщик кладёт в первую подходящую дыру независимо от индекса в порядке, поэтому «позиция» drop'а — это индекс порядка, а не пиксели, и выбрать конкретную дыру нельзя (это возможно только с настоящими пустотами, как в W10M, — вопрос Q6 в STATE.md, не решён). Решение по (а): над пустым местом цель — `HoverTarget.slot(i)`, где `i` — позиция вставки среди остальных элементов базового порядка (`0 ... count`). Её определяет клетка пальца `(строка, колонка)` в базовой раскладке (той же, что у хит-теста; сам элемент стоит на базовом месте, в счёт не входит): элемент встаёт сразу после последней плитки, чей левый верхний угол не позже этой клетки в порядке чтения; правее последней плитки и под сеткой — в конец, выше первой строки — в начало, в дыре — между плитками, которые она разделяет по порядку чтения; зазор между клетками принадлежит клетке слева/выше. Над плиткой по-прежнему E8.4 (`.reorder`: перетаскиваемая встаёт на слот цели), над собственным базовым слотом — `.none` (превью не меняется, «c»). Превью (`TileLayoutEngine.previewOrder(items:draggingID:insertionIndex:)`) следует за пальцем и анимируется как обычное push-превью; drop читает индекс из превью (`previewIndex(of:)`) и для выноса из папки (`moveBetweenFolders(_:to: nil, at:)`), и для обычной перестановки (`moveItem`), поэтому ярлык ложится ровно в показанный кадр (после канонизации порядка раскладка та же). На подъёме превью не трогается, пока палец не сместится больше чем на 12 pt от точки захвата (`emptySlotActivationDistance`): иконка панели после её закрытия обычно стоит над пустым местом, и слот не должен «убегать» из-под пальца в тот же кадр. Хит-тест E11.7, зоны E8.6 и магнит E8.9 не менялись; RTL — клетка считается в логических координатах. Покрыто `DropSlotTests` (конец, зазор между плитками, выше первой строки, под плитками, дыра, распад папки из одного ярлыка, обычный drag, RTL, подъём) и адаптированными `DragSessionTests`.

До тех пор настоящих дыр в файле, записанном этим кодом, нет — они появятся только после E14.5; чтение файлов с дырами и проекция уже работают. Тесты: `TileStorePlacementTests`.

50. **§3 «Размещение по координатам: чистый слой движка» (E14.2, 13.11.2026, D30–D31).** В `TileLayoutEngine` добавлен слой над набором `TilePlacedItem` (`id`, размер, `TileGridPlacement`): `slots(placements:columns:unit:fitting:)`, `validate`/`hasOverlaps`, `clamped(cell:size:columns:)`, `inserting(id:size:at:into:columns:)`, `resizing(id:to:in:columns:)`, `removing(id:from:)` (без репака — дыра остаётся), `collapsingEmptyRows(in:columns:)`, `newRowCell`/`firstFreeCell`, а для панели папки — варианты `folderBandEndRow(forFolder:…)`, `folderPanelInsertionIndex(placements:…)` и `rowsBelowOffset(placements:…)` по готовым ячейкам (старые сигнатуры живут). Следом плитки считается ужатый `fittingSize`; ячейка ограничивается холстом так, что колонка только сдвигается влево. Коллизии (D31): вставляемый прямоугольник `R` встаёт на ограниченную ячейку; остальные элементы обходятся в порядке чтения исходных позиций и каждый, пересекающий уже размещённое (`R` и ранее обработанные), опускается в той же колонке на нижнюю границу самого нижнего препятствия, пока пересечений нет (каскад); горизонтально никто не двигается, дыры вне затронутой области нетронуты; рост плитки идёт тем же путём, уменьшение оставляет дыру. Пустая строка (её не покрывает ни один прямоугольник, включая высокие плитки) схлопывается только вызовом `collapsingEmptyRows` — слой правки зовёт его на drop (E14.5). Слой никем не используется до E14.3–E14.6, поведение приложения не меняется; старый индексный API (`pack`, `repack`, `resizing`, `previewOrder`, `resizePlacement`) остаётся до E14.5. Тесты: `TileLayoutEnginePlacementTests`, `TileLayoutEnginePlacementPropertyTests`, `TileLayoutEngineFolderPlacementTests`.

51. **§3 «Таблица явных ячеек в снимке: раскладка по координатам» (E14.3, 13.11.2026, D30–D31).** `TileGridSnapshot` получил необязательную «боковую» таблицу `placementTable` (`TileGridPlacementTable`: идентификатор → `TileGridPlacement` в логических, незеркальных координатах, плюс заявленная ширина холста `columns`); перечисление `TileGridItem` не менялось (это source-breaking). Таблица попадает в раскладку через `TesseraTileGridView` (единственная точка `pushDisplayItemsToLayout`), входит в `GeometryKey` (ячейка каждого элемента и заявленная ширина), поэтому смена одних ячеек — изменение раскладки: в `update(snapshot:animated:)` она идёт веткой «тот же состав» и переезжает batch-анимацией bounce-кривой, как перестановка; снимок без изменений ключ не меняет, кадры не пересчитываются. Правило отката одно на раскладку и на вспомогательные расчёты (`TileGridPlacementTable.resolve`): таблицы нет, элементов нет, заявленная ширина не равна числу колонок сетки, ячейки нет хотя бы у одного элемента (лишние id игнорируются) или набор не проходит `TileLayoutEngine.validate` (выход за холст, отрицательная ячейка, пересечение) — тогда таблица игнорируется **целиком** и сетка раскладывается прежним `pack` по порядку (частичной подстановки нет). Иначе слоты берутся из `TileLayoutEngine.slots(placements:…fitting: true)`: плитки на своих ячейках, дыры сохраняются, обратного заполнения нет; большая плитка на узкой сетке ужимается, а не пропускается; высота контента — нижняя граница самой нижней занятой строки (пустые хвостовые строки не считаются, пустые строки над плиткой остаются). Панель раскрытой папки (D17/D18) при явных ячейках **не делает репак**: полоса папки (`folderBandEndRow(forFolder:…)`) и всё выше остаются на месте, всё, что начинается ниже полосы, остаётся на своих ячейках (дыры между строками и под панелью сохраняются) и сдвигается вниз на высоту панели и зазор (`rowsBelowOffset(placedSlots:…)`); индекс панели в наборе коллекции — `folderPanelInsertionIndex(placements:…)`. Без применимой таблицы блок панели прежний: строки ниже полосы переупаковываются под панелью. RTL: ячейки логические, зеркалирование остаётся в раскладке (внутри ширины сетки), в хранилище и движке его нет. `baseContentFrames(for:placementTable:)` берёт слоты из того же источника (по умолчанию `nil` — упаковка, поведение вызывающих не менялось); `baseInsertionIndex` остался на пути по порядку и после E14.5 координатором не используется (его удалит E14.6), `magnetSlotCenters` с E14.5 считает занятые строки по таблице ячеек, а при раскрытой папке магнит по-прежнему пуст. В E14.3 хранилище было **не подключено** (`TileStore.snapshot()` таблицу не прикладывает); с E14.5 штатные пути (координатор, Example, `TileStore.onChange` при известной ширине, фасад) строят снимок `snapshot(columns:)` — п. 53. Причина: ширина сетки в `snapshot()` неизвестна, а картинка не была бы доказуемо прежней — `setCatalog` ставит новые ярлыки в новую строку в конце холста, а не в дыру упаковки, и изменение размера дескриптора каталога не пересчитывает ячейки; снимки drag-превью координатор строит сам, и им таблица не нужна (превью — упаковка по порядку). Для хоста добавлен необязательный `TileStore.snapshot(columns:)` (ячейки из `placements(forColumns:)` и заявленная ширина); подключение штатных путей — в E14.5. Тесты: `TilePlacementLayoutTests`, `TilePlacementGridTests`.

52. **§3/§5 «Операции модели по ячейкам» (E14.4, 13.11.2026, D20, D30–D33).** *[имена до E14.6: `resizeInPlace` → `resize`, `pinTileToNewRow` → `pinTile` (таблица в п. 54); вынос последнего ярлыка не распускает папку — до D45, см. п. 56]* `TileStore` получил координатный слой операций над видимыми верхнеуровневыми элементами; ширина хоста `columns` передаётся явно. Публично: `moveItem(_:toCell:columns:)`, `moveItemToNewRow(_:columns:)`, `resizeInPlace(_:to:columns:)` (отдельное имя: `resize(_:to:columns:)` занято прежней операцией по порядку), `addToFolder(_:folderID:columns:)`, `extractFromFolder(_:toCell:columns:)`, `extractFromFolderToNewRow(_:columns:)`, `moveBetweenFolders(_:to:columns:)`, `unpin(_:columns:)`, `pinTileToNewRow(_:columns:)`, `collapseEmptyRows(columns:)`; для внутреннего использования — `createFolder(from:onto:title:columns:)` (возвращает `AtomicFolderResult`, как атомарный `createFolder(withTile:adding:)`). Схлопывание пустых строк — только вызовом `collapseEmptyRows`, который слой правки зовёт на drop (D31); остальные операции строк не схлопывают. После операции ячейки видимых элементов пишутся как посчитал движок, `canvasColumns` = `columns`, а порядок модели (`gridOrder`, он же порядок снимка) — порядок чтения ячеек (строка, колонка), так что старые потребители остаются согласованы; невидимые ключи хранят свои ячейки и в коллизиях не участвуют (п. 49). 53. **§5 «Drag по ячейкам: цель — клетка под пальцем, превью от базы, фиксация drop'а» (E14.5, 13.11.2026, D20, D21, D30–D33).** Координатор целиком работает на ячейках; прежние индексные операции `TileStore` и порядок канонизации им больше не используются (код остаётся до E14.6). **Цели** (`HoverTarget`): `.cell(TileGridPlacement)`, `.newRow`, `.group(id)`, `.folder(id)`, `.sourceFolder`, `.none` (вместо `.reorder`/`.slot`). Хит-тест — по **базовой** раскладке (базовые размещения на захвате, кадры не сдвигаются превью, E11.7): клетка под пальцем (`TesseraTileGridView.baseCell(forGridPoint:)`; логическая колонка, в RTL — после отражения; колонка ограничена `0 ..< columns`, строка не меньше 0). Клетка занята другим элементом: центр (25 %, `isPointInDropCenter`) — слияние (`.group` для ярлыка, не взятого из папки; `.folder` для чужой папки, папку в папку бросить нельзя; `.sourceFolder` для родной папки), всё остальное, включая зазоры, — `.cell` с **ячейкой элемента-цели** (перетаскиваемый встаёт на неё, цель выталкивается вниз, D31). Клетка пуста — `.cell` с клеткой под пальцем (ограничение холстом делают превью и операция); ниже последней занятой строки — `.newRow`; собственная базовая ячейка и вне сетки — `.none`; пока палец не сместился от точки захвата на 12 pt, пустые клетки цели не дают (подъём из панели). При раскрытой панели папки (в том числе во время анимации закрытия) раскладка сетки не базовая: элемент ищется по рамкам сетки, его ячейка берётся из базовых размещений, над панелью и над пустым местом цели нет. **Превью** считается каждый раз от базовых размещений, не от прошлого превью: для `.cell` — `TileLayoutEngine.inserting` (мешающие вниз каскадом), для `.newRow` — вставка на `newRowCell` (без исчезающей папки-источника, как у хранилища), для `.group`/`.folder`/`.sourceFolder`/`.none` — **база целиком** (раньше оставалось прежнее превью, и цель слияния «убегала» из-под пальца). Сетке уходит тот же порядок элементов с **таблицей ячеек** превью (`TileGridPlacementTable`, п. 51): соседи переезжают прежней batch-анимацией, пустышка — на новую ячейку; пустые строки во время drag не схлопываются. Магнит (E8.9) притягивает снимок к рамке ячейки-цели для его размера (`TesseraTileGridView.baseFrame(forCell:size:)`, ячейка ограничена холстом), условия включения и радиус прежние; над целями слияния и при Reduce Motion — нет; `magnetSlotCenters` считает занятые строки по таблице ячеек. Drag из панели папки: у синтетического ярлыка нет ячейки в модели — он встаёт на первую свободную ячейку после ячейки папки (рядом с ней, если справа свободно), так что снимок и таблица полны. **Фиксация drop'а**: `.cell` — `moveItem(_:toCell:columns:)` (ярлык из папки — `extractFromFolder(_:toCell:columns:)`), `.newRow` — `moveItemToNewRow`/`extractFromFolderToNewRow`, `.group` — `createFolder(from:onto:title:columns:)` (папка 2×2 на ячейке цели, одобрение D14 как прежде), `.folder` — `addToFolder(_:folderID:columns:)` (из папки — `moveBetweenFolders(_:to:columns:)`), `.sourceFolder` и `.none` — no-op; без выдержанного удержания слияние тоже no-op (E9.5). После удачной операции вызывается `collapseEmptyRows(columns:)`; отмена и drop без изменений возвращают базу, модель не пишется. Делегат получает `didMove(toIndex:)` с индексом в порядке чтения ячеек после операции. Кнопки правки идут теми же операциями: стрелка размера — `resizeInPlace`, открепление — `unpin(_:columns:)`, закрепление из списка приложений — `pinTileToNewRow`, и после изменения схлопывается только полностью пустая строка. Публичные методы координатора с индексом (`move(_:toIndex:)`, `moveBetweenFolders(_:to:at:)`) переводят индекс в ячейку: элемент встаёт на ячейку того, кто стоит на этом индексе среди остальных, индекс за концом — новая строка, вынос без индекса — ячейка папки (если ярлык в ней последний) либо первая свободная после неё. **Живое подключение**: штатные пути строят снимок `TileStore.snapshot(columns:)` — координатор (сверка, drag, отмена), `TileStore.onChange` (таблица прикладывается, когда хранилищу известна ширина сетки: её сообщает координатор при создании, на входе в правку и при смене `grid.columns`), Example и фасад (`StartScreenView` применяет снимок, у которого сменились только ячейки; снимок без таблицы показанную не затирает); хост, построивший сетку без таблицы, получает ячейки модели на входе в правку. Смена колонок во время правки пересобирает сетку (проекция без дыр при другой ширине холста, D32) и отменяет идущий drag. Для публичного `createFolder(withTile:)` добавлена внутренняя операция по ячейкам `TileStore.createFolder(withTile:title:columns:)`. Известные расхождения превью и итога: ярлык, выносимый из папки из одного ярлыка, и `.cell`-цель, перекрывающая пустую плитку-папку, — в превью папка-призрак выталкивается вниз, в итоге её уже нет. Тесты: `TileCellDragTests`, `TileCellWiringTests`, `DropSlotTests`, `DragSessionTests`.

55. **§9 «Порядок VoiceOver по ячейкам и фокус после правки» (E14.7, 13.11.2026, D30–D33).** Как было: порядок обхода VoiceOver определяется порядком индексов коллекции — сетка не задаёт `accessibilityElements` и не сортирует кадры, а `layoutAttributesForElements(in:)` раскладчика отдаёт атрибуты по индексу (поведение UIKit при этом на устройстве с VoiceOver не проверялось); индексы шли в порядке `snapshot.items`, то есть в порядке `gridOrder`. `gridOrder` совпадал с порядком чтения ячеек только после первой операции: после `load()`, миграции v1 → v2, `setCatalog` и проекции под другую ширину (D32) его никто не пересортировывал, и VoiceOver мог читать плитки не в том порядке, в каком они лежат на экране. Как стало: порядок чтения — строка по возрастанию, затем логическая колонка (0 — начало чтения, поэтому в RTL порядок тот же, меняются только кадры); пересечений нет, ничьих не бывает. (а) `TileStore.snapshot()` и `snapshot(columns:)` сортируют элементы по ячейкам — сохранённым либо, для другой ширины хоста, по ячейкам проекции (`placementReadingOrder(forColumns:)` читает тот же порядок); `gridOrder` остаётся порядком записи файла и разрешения ничьих. (б) Сетка (`reload`/`update`) сама приводит порядок снимка к порядку чтения, если снимок несёт применимую таблицу ячеек (`TileGridSnapshot.readingOrdered(columns:)`): так порядок верен и у хоста, у которого есть только `TileGridPlacementTable`; смена `columns` пересортировывает набор, если таблица стала применимой. Без применимой таблицы (нет, неполная, другая ширина, пересечения) порядок остаётся таким, как отдал хост, — `pack` раскладывает по порядку. Следствие: порядок `grid.items` во время drag-превью следует за ячейками превью, а не за базой; координатор сравнивает ожидаемые снимки с сеткой в том же порядке. (в) Панель папки (D17) — после последнего элемента полосы папки в порядке чтения (правило `folderPanelInsertionIndex(placements:…)`, E14.2); ярлыки папки читаются внутри панели, то есть после плитки папки. (г) Фокус `.layoutChanged` выбирает координатор и по-прежнему публикует его на следующем проходе runloop (B6): после unpin — следующий элемент в порядке чтения после удалённого (предыдущий, если он был последним; сама сетка, если на ней никого не осталось); цель выбирается по идентификатору до удаления, а не по индексу «на месте удалённого» — открепление оставляет дыру, и на этом месте может не быть никого; после resize, переноса/drop, выноса из папки — на изменённый/переехавший элемент; после слияния/добавления в папку — на папку; на несуществующий элемент фокус не уходит. Открепление ярлыка, лежащего в папке (на сетке его нет), как и раньше, переводит фокус на последний элемент сетки. (д) Custom actions («Открепить», «Изменить размер», действия папок, «Убрать из папки») не менялись: они зовут те же публичные операции координатора, уже работающие по ячейкам; новых действий нет (E15). Тесты: `TileAccessibilityOrderTests`; ожидания порядка `gridIDs` во время drag-превью в `DragSessionTests`, `DropSlotTests`, `TileCellDragTests` теперь — порядок чтения ячеек превью.

56. **§5/§6/§9 «Папка не бывает из 0–1 ярлыков: распад, превью drag, фокус» (E14.8, 13.11.2026, D45).** Как было: папка с одним оставшимся ярлыком сохранялась (п. 52, W10M §6.9 «осталась одна плитка» не описано); открепление ярлыка из папки переводило фокус на последний элемент сетки (п. 55 г); действий для ярлыков панели, кроме «Убрать из папки»/«Переместить», не было (п. 55 д, п. 37). Как стало (уточняет эти места): (а) **Модель.** Когда операция убирает ярлык из папки и в ней остаётся один, папка распускается: оставшийся ярлык становится верхнеуровневым элементом на ячейке папки со своим размером (`sizes`/каталог, ужатый под холст) через `TileLayoutEngine.inserting` — бо́льший (wide/large) выталкивает соседей вниз (D31), у правого края колонка сдвигается влево, меньший оставляет дыру; пустая папка исчезает. Правило — в `extractFromFolder`/`extractFromFolderToNewRow` (оставшийся ярлык встаёт **до** вынесенного, поэтому вынос на саму ячейку папки вытесняет его вниз, а «новая строка» считается с ним), `unpin` ярлыка из папки, `moveBetweenFolders` (источник распускается, папка-цель может быть вытолкнута вниз), чистке по каталогу (`setCatalog`/`load`: структурный распад плюс расчёт `inserting`, если ячейки уже корректны, иначе коллизии разрешает `reconcilePlacements`) и загрузке файла (папка из 0–1 ярлыков восстанавливается так же; если каталог ещё не зарегистрирован, одноярлычная папка ждёт `setCatalog`, чтобы не превратить удалённое приложение в невидимый ключ). Невидимых членов у папки после чистки по каталогу не бывает (каталог авторитетен), поэтому правило считает только видимые ярлыки. Исключение — переходная папка публичного `createFolder(withTile:title:columns:)` (один ярлык до `addToFolder`): ей правило не навязывается, пока из неё не убирают ярлык (тогда она исчезает), и при `setCatalog` она не затрагивается. Одно уведомление и одна запись на операцию, `gridOrder` — порядок чтения ячеек. (б) **Делегат.** `tileEditCoordinator(_:didDissolveFolder:remainingTile:)` (пустая реализация по умолчанию) вызывается один раз после успешной операции координатора и после её основного колбэка (`didUnpin`, `didMove(_:toFolder:atCell:)`); распад из `setCatalog`, `load` и вызовов `TileStore` в обход координатора хосту виден только в снимке `onChange`. (в) **Превью drag из панели.** Для папки из двух ярлыков сессия на захвате считает «итоговую картину» (`DragFolderDissolution`: элементы с оставшимся ярлыком вместо папки и размещения модели без выносимого ярлыка с оставшимся на ячейке папки): на цели-размещении (`.cell`, `.newRow`) превью показывает именно её, а выносимый ярлык встаёт по обычным правилам от этих размещений (те же шаги, что у `TileStore`, поэтому drop кладёт ярлыки туда, где показало превью); «новая строка» считается с оставшимся ярлыком. Пока цель — слияние с другой папкой, родная папка или её нет, показывается база (папка с оставшимся ярлыком, как при подъёме): слияние применяет распад только на drop. Отмена, отказ хоста и drop без цели возвращают сетке модель с исходной папкой (`restore()`). Превью каждый раз считается от базы, без накопления. (г) **Панель и фокус VoiceOver.** `unpin` ярлыка из раскрытой панели (публичный метод и новое VoiceOver-действие «Открепить» на ярлыках панели): если папка распадается, раскрытая панель закрывается штатным `closeFolder` (анимированно, при Reduce Motion мгновенно) **до** применения снимка, а снимок без папки сетка применяет после перехода (E10.2); фокус — на оставшийся ярлык (новый элемент сетки). Если папка переживает — панель остаётся, фокус на **следующем** ярлыке панели в порядке отображения, у последнего — на предыдущем; панель закрыта — на плитке папки. Пост `.layoutChanged` — на следующем проходе runloop после конца перехода панели и применения отложенного снимка (внутренний шов `TesseraTileGridView.performAfterFolderTransition`), потому что закрытие панели само ставит фокус на плитку папки, которой уже нет. `moveBetweenFolders(_:to: nil)` распускает папку из двух так же (панель закрывается, фокус на вынесенном ярлыке). Тесты: `TileStoreFolderMinTwoTests`, `TileFolderDissolveUITests`; существующие тесты, закреплявшие «папка из одного ярлыка остаётся», переведены на папки из трёх ярлыков либо на ожидание распада.

57. **§5/§6/§9 «Кнопка открепления на ярлыках панели папки» (E15.9, 13.11.2026, D46).** Как было: убрать ярлык из папки зрячий пользователь мог только перетаскиванием из панели (п. 37, E11.1); на ярлыках панели в правке виджетов не было, только действия VoiceOver (п. 56). Как стало: (а) **Кнопка.** В правке у каждого ярлыка раскрытой панели — тот же оверлей `TesseraTileEditControlView`, что и на плитках сетки, но только с кнопкой открепления: диаметр считается по тем же правилам от размера ярлыка (не меньше 20 pt, потолок `controlDiameter`), центр у угла рамки, выступ 4 pt (D48; на момент задачи — 6 pt); стрелки размера у члена папки нет, у самой плитки-папки кнопки открепления по-прежнему нет (D38). Оверлеи живут в том же обрезающем контейнере, что и десктопные (`panelEditControls`), и скрыты от VoiceOver, действие «Открепить» на ярлыке панели осталось. (б) **Угол — один помощник.** Рамку кнопки выбирает статическая `TesseraTileEditControlView.unpinButtonFrame(inTileBounds:side:isRightToLeft:)`, её зовут и сетка, и панель: перенос кнопки в правый верхний угол (D29, E15.2) — правка одной функции. (в) **Правило касания.** Зона кнопки ярлыка панели — угловая четверть ярлыка плюс выступ наружу не дальше зазора сетки (≤ 4 pt после D48, п. 60; на момент задачи ≤ 6 pt), квадрат не меньше 44 pt прижат к внешнему углу и растёт внутрь, но не дальше осей ярлыка (минус 1 pt): у ярлыка ≈ 55 pt это ≈ 30 pt (при выступе 6 pt было ≈ 32 pt). Центр и тело ярлыка кнопке не принадлежат: тап по ним ничего нового не делает, long-press поднимает ярлык для выноса (жест координатора не стартует только на самой кнопке, как и на сетке); в RTL четверть зеркальна. Когда зоны нескольких оверлеев пересекаются (кнопка панели и кнопка плитки сетки), побеждает кнопка с ближайшим к точке центром; без оверлеев панели порядок прежний (по порядку подвью). (г) **Жизненный цикл.** Кнопки появляются, когда панель устоялась (сетка зовёт `folderPanelStateDidChange` на начале и конце перехода), проявляются 0,18 с (Reduce Motion — сразу), снимаются в начале закрытия панели, при распаде, при drag из панели (панель закрывается мгновенно) и вне правки; на прокрутке и после `refreshEditControls()` идут за рамками ярлыков (`panelShortcutGeometry()`). (д) **Тап.** `unpinPanelTile`: снимок иконки улетает (как на сетке; при Reduce Motion — без полёта), затем обычный путь ярлыка папки — `performImmediateUnpin`: `TileStore.unpin`, `collapseEmptyRows`, `didUnpin`, при двух ярлыках — распад D45 и `didDissolveFolder`, фокус по E14.8; повторные тапы во время полёта игнорируются, закрытие панели в полёте отменяет открепление. Публичное `unpin(_:)` и действие VoiceOver остаются мгновенными, без полёта. Ярлыки панели, как и раньше, не качаются и не затемняются (виджеты правки на них — только кнопка). Не проверено на устройстве: удобство зоны касания на ярлыках 55 pt, VoiceOver, анимация полёта и проявления в кадре (PLAN «Ручная проверка E14»). Тесты: `TilePanelUnpinButtonTests`.

58. **§5 «Жест фона не принимает касания внутри зоны кнопок правки» (E15.10, 13.11.2026).** Как было: кнопки «открепить»/«размер» плитки сетки выступают за рамку плитки на `cornerOverhang` (6 pt на момент задачи, с D48 — 4 pt, п. 60; п. 42), то есть в зазор между плитками, а зона касания расширена до 44 pt. `backgroundTapRecognizer` (тап по пустому месту — выход из правки, `cancelsTouchesInView = false`) принимал любое касание в правке, а решение «пусто ли под пальцем» брал по `item(at:)` сетки; зазор — не плитка, поэтому тап по выступающей части кнопки срабатывал и по кнопке (ярлык откреплён / размер сменён), и как «тап по пустому месту» — правка неожиданно заканчивалась. Как стало: в `gestureRecognizer(_:shouldReceive:)` жест фона отклоняет касание, если оно попадает в зону любой кнопки правки (плитка сетки или ярлык панели, выступ в зазор и расширенная зона включены); решение принимает `hitTest` контейнера кнопок — тот же код, которым кнопки получают касания (`hitFrame(for:)`, `panelUnpinHitZone`, RTL-зеркалирование, наложения оверлеев), поэтому жест и кнопки не могут разойтись. Тап по пустому месту вне всех зон выходит из правки, тап по телу плитки — как раньше; `cancelsTouchesInView`, включение жеста только в правке, размеры и углы кнопок, long-press и drag не менялись. Решение вынесено в `performBackgroundTap(at:)` для тестов (поведение обработчика то же). Кнопки панели выход из правки и раньше не вызывали (панель — полноширинная ячейка, `item(at:)` не пуст), правило для них — единое. Не проверено на устройстве (PLAN «Ручная проверка E14»). Тесты: `TileEditButtonGapTapTests`.

59. **§4/§5 «Углы бэйджа и кнопок правки, цикл размеров» (E15.1–E15.3, 13.11.2026, D28, D29).** Как было: бэйдж — в верхнем углу у конца строки; кнопка открепления — в верхнем углу у начала строки (левый в LTR), стрелка размера — в нижнем у конца; цикл размеров шёл порядком `TileSize.allCases` (small → medium → wide → large), который никто не выбирал. Как стало: **углы.** Бэйдж (капсула и `.dot`; ячейка сетки и живая плитка — одной раскладкой `TesseraTileBadgeLayout`) — в нижнем углу у конца строки (правый в LTR, левый в RTL), поле как у подписи. Кнопка открепления — в верхнем углу у конца строки (правый в LTR), стрелка размера — в нижнем той же стороны; угол открепления по-прежнему выбирает один помощник `unpinButtonFrame(inTileBounds:side:isRightToLeft:)`, поэтому сетка и панель папки (D46) переехали вместе; зона касания кнопки ярлыка панели — зеркальная угловая четверть. **Подпись и бэйдж.** Подпись делит нижний ряд с бэйджем и уступает место: пока ей остаётся не меньше 60 % ширины контента и не меньше 40 pt — остаётся в нижнем ряду, но уже на ширину бэйджа с зазором 4 pt («рядом»); иначе (узкая плитка, у которой рядом не остаётся места) остаётся полной ширины и поднимается над рядом бэйджа («над»); если при этом не хватает высоты, иконка уступает подписи по прежнему правилу «текст важнее». **С D47 (п. 60) малая плитка 1×1 с иконкой и видимым бэйджем подпись не рисует вообще: остаются иконка и бэйдж; «над» остаётся у 1×1 без иконки и у плиток побольше с широкой капсулой.** Способ выбирается по геометрии вне правки и в правке не меняется. Dynamic Type, правило «99+», точка и «0 скрыт» не менялись; плитка папки бэйджа не показывает (E15.7), мини-бэйджи внутри превью папки не менялись. **Бэйдж и стрелка в правке.** Стрелка заходит внутрь плитки на `диаметр − выступ` (на 1×1 ≈ 16 pt при выступе 4 pt, D48; при 6 pt было ≈ 14 pt); бэйдж сдвигается вдоль нижнего ряда от угла на эту величину плюс 2 pt (анимация 0,18 с, при Reduce Motion — сразу; сетка хранит отступ по идентификатору, как дим): зазор между рамками бэйджа и стрелки — ровно 2 pt на всех плитках, ширинах 375/390/402/414 pt (6 колонок) и для капсулы, «99+» и точки. Исключение: капсула «99+» (34 × 18 pt) на 1×1 не помещается правее стрелки (плитка уже 58 pt; при выступе 6 pt это было при ширинах ≤ 402 pt, после D48 — на всех четырёх ширинах 375–414 pt, п. 60) и **скрывается только на время правки** (поднять её между кнопок значило бы выдавить подпись 1×1). **Правило владения зонами касания** (две кнопки у конца строки: на 1×1 их зоны 44 × 44 pt пересеклись бы на ≈ 1,5–2 pt): зона — рамка кнопки, расширенная до 44 pt вокруг центра; открепление владеет **верхней половиной** высоты плитки, стрелка — **нижней**; обе зоны не заходят за вертикальную ось плитки (минус 1 pt) — центр и тело плитки (тап, long-press, drag) не принадлежат никому; на плитках от 62 pt зоны остаются полными 44 × 44 pt, на 55 pt — ≈ 42,5 × 43,5 pt, на 50 pt — ≈ 40 × 41 pt (D48: центр кнопки ближе к оси плитки на 2 pt; при 6 pt было 55 pt — 44 × 44, 50 pt — ≈ 42 × 43). Пересечения зон соседних плиток (стрелка верхней и открепление нижней стоят в одной колонке, зазор 8 pt, выступ 4 + 4 pt после D48: круги касаются; при 6 + 6 pt они перекрывались на 4 pt) решает **ближайший центр кнопки** — теперь для любых оверлеев, а не только с панелью; жест фона E15.10 использует тот же `hitTest` и не менялся. **Цикл размеров** — явный `TileSize.cycleOrder` = small → wide → medium → large и `TileSize.next(among:)`: идёт вперёд по кругу к первому размеру из набора, пропуская недоступные; единственный поддерживаемый размер замыкает цикл на себе; текущий размер вне набора — ближайший дальше по циклу. Хост через `supportedSizesProvider` задаёт набор, а **не порядок** (раньше порядок списка хоста был порядком цикла). Формат `tiles.json` не менялся; стрелка и действие VoiceOver «Изменить размер» вызывают один и тот же `cycleSize(of:)`, поэтому применяют и озвучивают один размер. Правка после шага не завершается (D27). Тесты: `TileBadgeCornerTests`, `TileEditCornersTests`, `TileSizeCycleTests`; мигрированы `TileEditTests`, `TileResizePushTests`, `TileCellWiringTests`, `TileAccessibilityOrderTests`, `DragSessionTests`, `TilePanelUnpinButtonTests`, `TileEditButtonGapTapTests`. Не проверено на устройстве (PLAN «Ручная проверка E14»).

60. **§4/§5 «Малая плитка с бэйджем: иконка и бэйдж; выступ кнопок правки 4 pt» (E15.11, E15.12, 13.11.2026, D47, D48).** Как было: на плитке 1×1 подпись шла над рядом бэйджа и выдавливала иконку (п. 59: «текст важнее»), поэтому «Почта» с бэйджем «3» была без иконки; кнопки «открепить»/«размер» выступали за рамку плитки на 6 pt, и круги вертикальных соседей одной колонки (стрелка верхней плитки и открепление нижней) перекрывались на 4 pt. Как стало: (а) **1×1 с бэйджем (D47, как в W10M).** Если ярлык в модели малый (`TileSize.small`), у него есть иконка и бэйдж виден (капсула «3», «99+» или `.dot`; «0» бэйджем не считается), подписи нет — остаются иконка и бэйдж: раскладка `TesseraTileBadgeLayout` получила способ `iconAndBadge` и рамку иконки `smallTileIconFrame(tileSize:inset:bottomReserve:)` — иконка по центру верхней зоны над рядом бэйджа (зазор 4 pt), бэйдж — в нижнем углу у конца строки, как раньше. Сторона иконки — высота зоны, но не больше 45 % меньшей стороны, 34 pt и ширины между кнопками правки (иконка не заходит под кнопку открепления и в правке не двигается), не меньше 12 pt (при раздутом Dynamic Type бэйдж ложится поверх иконки, иконка остаётся). На ширинах 375/390/402/414 pt (6 колонок) иконка 16/19/21/23 pt для капсулы и 17/20/22/24 pt для точки. Решение принимает ячейка по **размеру в модели**, а не по геометрии: на любой ширине сетки малая плитка ведёт себя одинаково, плитки 2×2, 4×2, 4×4 не затронуты. Подпись скрыта только визуально: label и value VoiceOver не менялись. Малая плитка без бэйджа, с «0» и без иконки подпись сохраняет (без иконки на плитке не осталось бы ничего, кроме бэйджа). Живая плитка (`TesseraLiveTileView`): ячейка выставляет `isSmallTile`, и **каждая сторона** решает сама — сторона с иконкой при бэйдже рисует иконку (хотя обычно иконку стороны прячут на плитке уже 80 pt) и скрывает заголовок и подпись, сторона без иконки сохраняет текст; самостоятельный контейнер вне сетки не меняется. В правке бэйдж по-прежнему сдвигается от стрелки размера (зазор 2 pt), подпись не возвращается; правило скрытия «99+» на 1×1 осталось (см. (б)). (б) **Выступ 4 pt (D48).** `TesseraTileEditControlView.cornerOverhang` = 4 pt — половина зазора сетки 8 pt: круги кнопок соседних плиток касаются (зазор 0), но не перекрываются, по вертикали и горизонтали, в LTR и RTL. От константы зависят рамки кнопок, зоны касания, обход бэйджа и допуск зоны кнопки ярлыка панели (`min(выступ, зазор)`); отдельных чисел нет. Следствия: стрелка заходит в плитку на 16 pt (было 14), бэйдж в правке сдвигается на 12 pt от поля (было 10), зазор бэйдж — стрелка по-прежнему 2 pt; капсула «99+» на 1×1 скрыта в правке на всех четырёх ширинах (была при ≤ 402 pt); зоны касания у оси плитки обрезаны глубже: 50 pt — ≈ 40 × 41, 55 pt — ≈ 42,5 × 43,5, от 62 pt — 44 × 44; зона кнопки ярлыка панели на ярлыке 55 pt ≈ 30 pt (было ≈ 32). Жест фона E15.10 считает по тому же `hitTest` и не менялся. Не проверено на устройстве (PLAN «Ручная проверка E14»). Тесты: `TileSmallBadgeIconTests`, `TileEditOverhangTests`; обновлены `TileBadgeCornerTests`, `TileEditCornersTests`, `TileEditControlsTests`, `TilePanelUnpinButtonTests`, `TileEditButtonGapTapTests`.
61. **§9 «Бэйдж-точка озвучивается» (E15.4, 13.11.2026, D34).** Как было: у `.dot` не было `accessibilityValue` (озвучивалось только число), и незрячий пользователь не узнавал о наличии уведомления. Как стало: `.dot` даёт value «есть уведомление» (en «has a notification», ключ `a11y.badge.dot`), label не меняется (в том числе скрытая визуально на 1×1 подпись, D47); число и `.none` — как раньше. Единый источник — внутренний `TileBadge.accessibilityValueText`: ячейка сетки, ярлык панели папки и автономная `TesseraLiveTileView` (текст хоста `accessibilityText` приоритетнее). Бэйдж папки — E15.7.
