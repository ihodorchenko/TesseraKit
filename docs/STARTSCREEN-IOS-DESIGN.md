# Рабочий стол (Start Screen) Windows Phone 10 для iOS — проектный дизайн

> Проектный документ: теоретическое проектирование компонента «Рабочий стол» по мотивам Windows 10 Mobile для iOS.
> Ограничения: **iOS 15+**, **Swift 5.9+**, допускаются UIKit и SwiftUI. Реализация в объём документа не входит.
> Парные документы: **PANORAMA-IOS-DESIGN.md**, **PIVOT-IOS-DESIGN.md**. Общие механики (пейджер, параллакс, арбитраж жестов) вынесены в общий слой: **CORE-IOS-DESIGN.md** (пакет **TesseraKit**, target `TesseraCore`).

## 0. Что проектируем

Рабочий стол Windows 10 Mobile (Start Screen):

- вертикальный скролл плиток + фоновые обои с параллаксом;
- live-плитки: флип (двусторонние), бейджи, живой контент;
- плитки 4 размеров: small 1×1, medium 2×2, wide 4×2, large 4×4;
- **свайп справа налево → список приложений (там же настройки)**;
- **свайп слева направо → хук вызова чего угодно** (в WP10 этого не было — расширение проекта);
- режим редактирования: «желе», unpin, resize, перетаскивание.

## 1. Ключевая архитектурная идея: три страницы

Горизонтальный мир рабочего стола — это **пейджер из трёх полноэкранных страниц**:

```
[ Левая страница (хук) ]  [ START ]  [ Все приложения + Настройки ]
```

Start — центральная, с неё свайп справа налево уводит в список приложений (в точности WP), слева направо — на страницу-хук. Всё, что спроектировано для Pivot, работает здесь без изменений: `UIScrollView.isPagingEnabled = true`, полноэкранные страницы — бесплатный снап, тот же инвариант `t = offset.x / pageWidth`. **Ядро Pivot переиспользуется почти дословно** — сильный аргумент за выделение общего core-пакета (см. §12).

Два нюанса против Pivot:

1. **Арбитраж жестов становится трёхсторонним**: пейджер хочет горизонталь, плиточная сетка — вертикаль, список приложений — вертикаль. Решение то же (вариант B из Panorama): в `gestureRecognizerShouldBegin` пейджера отдаём жест по доминирующей оси — горизонталь пейджеру, вертикаль ребёнку. Разница только в том, что правило применяется к двум детям.
2. **Левый край экрана занят системой**: если компонент живёт внутри `UINavigationController`, свайп слева направо дерётся с `interactivePopGestureRecognizer`. Политика: рабочий стол — **корневой экран без back-навигации** (как на WP), тогда оба края наши; если вложен в стек — системный жест отключаем или уступаем ему. Это ровно тот конфликт, который разбирался с edge pan.

## 2. Архитектура

```
StartScreenView (SwiftUI-фасад)
    └─ StartScreenViewController (UIKit)
        ├─ HorizontalPager (3 страницы, ядро Pivot)
        │    ├─ QuickPanelPage        ← левая страница-хук (пустая по умолчанию)
        │    ├─ StartPage
        │    │    ├─ TileGridView      ← UICollectionView + кастомный layout
        │    │    └─ TileBackgroundView ← обои + вертикальный параллакс
        │    └─ AppsListPage          ← jump-list приложений + настройки
        ├─ LiveTileEngine             ← таймеры флипа, контент-провайдеры
        ├─ TileEditCoordinator        ← железо, drag, resize, unpin
        └─ TileStore                  ← порядок/размеры, персистентность
```

Модель:

- `TileDescriptor` — id, размер (4 вида), контент (статичный или провайдер), позиция в сетке;
- `TileLayoutEngine` — раскладка в юнитах;
- `LiveTileContentProvider` — источник «живого» контента (фронт/бэк, обновления);
- `StartScreenDelegate` — события (тап, pin/unpin, переходы страниц, хук).

## 3. Плиточная сетка — самая сложная часть

**Модель раскладки.** Сетка `N` колонок (4 по умолчанию, опция 6 для больших экранов). Юнит:

```
unit = (screenWidth - margins - gaps × (N-1)) / N
```

Размеры плиток в юнитах: 1×1, 2×2, 4×2 (wide), 4×4 (large). Позиция хранится в **юнитных координатах** — тогда сетка автоматом пересчитывается под любую ширину экрана (поворот/iPad), а раскладка не зависит от пикселей.

**Алгоритм упаковки**: жадный, слева направо сверху вниз — ищется первая строка, куда прямоугольник плитки помещается целиком. **Дыры допускаются честно**: в WP10 они существовали (под wide/large плитками оставались пустые юниты). Это сильно упрощает алгоритм — никакого «идеального тетриса».

**Реализация** — кастомный `UICollectionViewLayout`:

- `layoutAttributes` считаются из модели (юниты → rect);
- изменения (resize, reorder) — через инвалидацию с контекстом + `performBatchUpdates`, тогда сдвиг соседних плиток анимируется UICollectionView сам;
- правило производительности из Panorama свято: в `scrollViewDidScroll` **только параллакс фона, никакого layout**.

**Почему не готовый flow-layout**: переменные размеры + «выталкивание» при перетаскивании + WP-вид сдвига — готовые layout'ы этого не дают, а кастомный тут выходит проще, чем подгонка.

## 4. Live-плитки (движок)

- **Контентная модель**: у плитки фронт (иконка/заголовок/счётчик/фон) и опциональный бэк. `LiveTileContentProvider` отдаёт контент и подписки на обновления (таймер, пуш, фаза сцены).
- **Флип**: контейнер с двумя слоями, `CATransform3D` + перспектива (`m34`), поворот по Y на 90°, подмена стороны, доворот. Только трансформы — layout не трогаем.
- **Стахгер**: плитки флипаются не одновременно, а батчами со случайным разбросом (у WP именно так; синхронный флип всего экрана выглядит дёшево).
- **Паузы**: плитка вне экрана (`layoutAttributes` видимости) — флип заморожен; приложение в фоне — заморожен; **Reduce Motion включён — флипов нет вообще**, показывается статичный фронт.
- **Бейдж** — маленький счётчик в углу (отдельный view, не часть флипа).
- Память: изображения декодируются в размер плитки и кешируются, иначе десяток живых плиток съест сотни мегабайт.

## 5. Режим редактирования

Три подзадачи, по возрастанию сложности:

1. **Вход и «желе»**: long-press → все плитки трясутся (как iOS home). Джиттер — `CAKeyframeAnimation` поворота ±2° на каждую плитку со случайной фазой; при Reduce Motion — не трясутся, только подсветка/X-кнопки.
2. **Unpin и resize**: крестик — открепление с fly-out анимацией; стрелка — циклическая смена размера (small → medium → wide → large → small, с учётом поддерживаемых плиткой размеров). Resize запускает переупаковку (п. 3) с анимацией.
3. **Перетаскивание** — самая багогенерирующая часть: снэпшот плитки едет за пальцем, соседние плитки «расступаются» с анимацией, при отпускании плитка встаёт в ближайшее валидное место. Стратегия: **собственный drag-координатор** (снэпшот + пустышка + переупаковка модели + инвалидация layout), а не нативный `UICollectionView` interactive movement — нативный заточен под равные ячейки и на переменной сетке даёт рваные анимации.

`TileStore` сохраняет порядок/размеры/закрепления (JSON/файл), выживает между запусками.

## 6. Страница справа: список приложений + настройки

- `UITableView` с секциями по буквам + `sectionIndexTitles` (jump-list) — нативный паттерн, ничего изобретать не надо.
- **Настройки — секция/элемент списка** (как на WP), при желании отдельный экран настроек внутри этой же страницы.
- **Двусторонняя связь с плитками**: pin из списка → плитка появляется в сетке; unpin на сетке → элемент списка меняет состояние. Источник истины — `TileStore`, обе страницы только читают/пишут его — то же правило «один писатель», что в Pivot.

## 7. Страница слева: хук

- Контейнер с протоколом `QuickPanelProviding` (или замыканием) — по умолчанию пустая заглушка.
- Примеры наполнения: быстрые настройки, поиск, профиль, недавние приложения — всё, что захочет приложение.
- Механика: пейджеру всё равно, что на странице; хук получает колбэки появления/скрытия, чтобы подгружать контент лениво.

## 8. Параллакс фона

Переиспользуется подход Panorama, но по вертикали: обои выше `contentSize` сетки, в `scrollViewDidScroll` — `backgroundOffset = offset.y × factor` (factor ≈ 0.4–0.6), только `frame`/`transform`. При Reduce Motion — статично. Направление на экране и расположение слоя — см. «Отступления реализации», п. 6.

## 9. Accessibility

- **Плитка** — один элемент: label из заголовка + состояния (счётчик), `UIAccessibilityCustomAction` для resize/unpin; в режиме редактирования озвучивается смена режима.
- **Страницы**: листание через `accessibilityScroll`; название страницы озвучивается.
- **Reduce Motion**: нет флипов, желе, параллакса.
- **Dynamic Type**: текст плиток и списка масштабируется; проверять, что на small-плитке текст усекается корректно.
- **RTL**: зеркалится сетка, пейджер и jump-list.

## 10. MVP и что отрезать

**Входит:**

1. Пейджер трёх страниц (ядро Pivot).
2. Сетка: 4 размера, жадная упаковка, кастомный layout.
3. Edit-режим: желе, unpin, resize, drag-перестановка.
4. Live-флип для простых текстовых плиток + бейджи + стахгер + паузы.
5. Список приложений с буквами + секция настроек, двусторонний pin/unpin.
6. Левая страница-хук.
7. Обои + параллакс.
8. SwiftUI-фасад, VoiceOver + Reduce Motion, персистентность TileStore.

**Отрезано в v1:** фото-слайдшоу в плитках, push-обновления контента, «идеальная» упаковка без дыр, peek-анимация, 6-колоночная адаптация, deep-links из плиток.

## 11. Риски

- **Drag-перестановка на переменной сетке** — главный источник багов; закладывать тесты на случайных конфигурациях плиток.
- **Жестовый стек** — самый сложный в проекте: горизонтальный пейджер × вертикальная сетка × вертикальный список × системный жест слева. Разруливается правилом доминирующей оси + политикой «корневой экран».
- **Флипы vs скролл** — джиттер при неаккуратной реализации; лечится только трансформами и паузами.
- **Культурный риск**: живой рабочий стол — самая «чужая» для iOS вещь из всех трёх компонентов; только как опциональный режим, не как дефолтная навигация.

## 12. Структура проекта: общий Core

У трёх компонентов накопился общий слой: инвариант `t`, пейджер с `pagingEnabled`, арбитраж жестов (вариант B), правило «никакого layout в скролле», SwiftUI-фасад. Предлагаемая структура (детали и контракты — в **CORE-IOS-DESIGN.md**):

```
TesseraKit (SPM-пакет)
├── TesseraCore        ← пейджер, параллакс, арбитраж жестов, фасады
├── TesseraPanorama    (свой снап, peek, фон)
├── TesseraPivot       (лента заголовков, индикатор)
└── TesseraStartScreen (сетка плиток, live-движок, 3 страницы)
```

## 13. Итог

Рабочий стол — композиция уже спроектированных механик (пейджер Pivot, параллакс Panorama, вариант B для вертикали) плюс два по-настоящему новых «монстра»: плиточная сетка с переменными размерами и live-движок. Сложность концентрируется в трёх точках: жадная упаковка в юнитах, drag-перестановка с анимацией «расступания» и дисциплина флипов (только трансформы, стахгер, паузы). Если эти три точки выдержать, остальное собирается из уже готовых деталей.

## 14. Уточнения MVP (29.10.2026)

Решения пользователя, уточняющие этот документ перед реализацией (полные формулировки — D12–D15
в [STATE.md](STATE.md)):

1. **Рабочий стол — ярлыки и папки.** Компонент выглядит как рабочий стол с ярлыками и папками;
   ярлык — **просто действие**: `id`, `title`, `icon`, `action: () -> Void`, опциональный `badge`
   (красная точка/счётчик внимания — как на WP). Поля `type` у ярлыка нет, группировка по типу
   не используется.
2. **Обе боковые страницы опциональны.** Левая (хук, `QuickPanelProviding`) и правая (список
   приложений/настроек) существуют, только если хост их задал; пейджер масштабируется от 1
   страницы (только START) до 3.
3. **Папки — через функцию одобрения.** Создание папки, добавление ярлыка в папку и перемещение
   между папками разрешает колбэк хоста (дефолт — разрешено).
4. **Live-плитки закладываются** (флипы, стахгер, паузы, Reduce Motion — §4 без изменений);
   размеры ярлыков — **4 вида**: 1×1, 2×2, 4×2, 4×4.

## Отступления реализации (v0.1, 29.10.2026)

> Сверка проектного документа с фактическим кодом релиза 0.1.0. Текст выше не переписывался: отступления зафиксированы отдельной секцией. Формат пункта: что обещал документ → что делает код → решение.

1. **§5 «Режим редактирования»: кто его подключает.** Документ (и схема §2) обещал, что редактирование — часть экрана: `TileEditCoordinator` внутри `StartScreenViewController`, long-press входит в режим «желе». Код: `TesseraStartScreenViewController` и `StartScreenView` координатор не создают и собственного API входа в редактирование не имеют — наружу открыта только сетка (`gridView`) как точка подключения координатора. Хост сам создаёт `TileStore` и `TesseraTileEditCoordinator(grid:store:configuration:)`, передавая сетку экрана (`public var gridView` контроллера), а координатор в инициализаторе сам вешает на неё long-press (0.45 с) и tap по фону; дальше хост вызывает `beginEditing()`, `endEditing()`, `toggleEditing()` тогда, когда считает нужным. Решение: в v0.1 режим редактирования — хост-опция поверх готовой сетки; владение координатором экраном отложено (так приложение, которому редактирование не нужно, не платит за координатор и его оверлеи).

2. **§2/§6 «Страница справа» и принадлежность `TileStore`.** Документ обещал: `AppsListPage` — часть экрана, `TileStore` — компонент экрана (схема §2), настройки — «секция/элемент списка». Код: правая страница — произвольная фабрика `() -> UIViewController` (решение D13); `TesseraAppsListPageViewController` — опциональный готовый класс (`make(store:settings:texts:)`), который хост может не использовать вовсе. Экран данных не хранит: `TesseraStartScreenViewController.configure(leftPanel:rightPage:)` и `StartScreenView.init(snapshot:style:leftPanel:rightPage:...)` принимают готовый снимок сетки (`TileGridSnapshot` через `reload(grid:)` в UIKit и `snapshot:` в SwiftUI), `TileStore` не создаётся и не удерживается. Настройки — строки хоста (`TesseraAppsListSettingsItem` с `id`/`title`/`subtitle`/`icon`/`action`), компонент не знает их смысла. Решение: `TileStore` живёт у хоста (единственный писатель), экран — презентационный слой; схему §2 читать как предлагаемую компоновку приложения, а не как состав библиотеки.

3. **§2 «Модель»: фактический состав `StartScreenDelegate`.** Документ обещал события «тап, pin/unpin, переходы страниц, хук». Код: в протоколе четыре события — `startScreen(_:didTapShortcut:)`, `startScreen(_:didTapFolder:)`, `startScreen(_:didChangePage:index:)`, `startScreen(_:didChangeHookVisibility:)`, все с пустыми реализациями по умолчанию (обязательных нет). Pin/unpin в делегате отсутствует: закрепление — операция модели (`TileStore.pin`/`unpin`, в том числе из опциональной страницы списка), а режим редактирования сообщает об откреплении через `TesseraTileEditCoordinatorDelegate` (`tileEditCoordinator(_:didUnpin:)` и соседние события resize/move/папок). Тап по ярлыку — событие, а не вызов `TileDescriptor.action` (D12): действие выполняет хост. Решение: актуальный контракт — четыре события выше; pin/unpin и редактирование — в `TesseraTileEditCoordinatorDelegate`; перечисление §2 оставлено как проектное намерение.

4. **§2/§3 «Модель раскладки»: где живут координаты.** Документ обещал: «Позиция хранится в юнитных координатах». Код: `TileStore` хранит только порядок элементов сетки (`gridOrder`), авторитетные размеры (`sizes`, размер папки в `FolderRecord`) и папки; `TileGridSnapshot.layoutItems` — пары «id + размер» в порядке сетки, без колонок и строк. Юнитные координаты вычисляются заново при каждой раскладке: `TesseraTileCollectionViewLayout` вызывает `TileLayoutEngine.unit(screenWidth:columns:gaps:)`, затем `TileLayoutEngine.pack(items:columns:unit:)` и `TileLayoutEngine.rect(for:unit:gap:origin:)`. То есть колонка/строка — производные от порядка, размеров и доступной ширины. Решение: координаты не персистятся — именно это делает поворот/iPad бесплатными; §3 в этой части трактуем как описание вычисляемой раскладки, а не формата хранения.

5. **§3 «Плиточная сетка»: «честные дыры» отменены — финальная раскладка строго компактная (E8.5).** Документ обещал жадную упаковку, в которой «дыры допускаются честно»: под wide/large плитками остаются пустые юниты, пока в них не поместится следующая плитка. Код: `TileLayoutEngine.pack` (публичный вход; реализация — `packCompact`) ставит каждую плитку в самую верхнюю-левую позицию, где она помещается целиком, и затем схлопывает раскладку вверх-влево до неподвижной точки (`stabilize`): ни одну плитку нельзя сдвинуть вверх или влево, пустых строк не остаётся. Свободный юнит остаётся только там, куда не помещается ни одна из **текущих** плиток (например, справа от 2×2, если следующая — 4×2); как только появляется плитка подходящего размера, она занимает это место, а после перетаскивания или открепления нижние плитки поднимаются в освободившееся место. Строгая компактность применяется и к обычной раскладке, и к edit/drag-переупаковке (обе идут через `pack`), поэтому визуал режимов не различается; панель раскрытой папки (D17) по-прежнему не упаковывается как плитка — она полноширинная строка под полосой папки (п. 11), а элементы под ней переупаковываются компактно. Решение: §3 в части «честных дыр» не действует — по спеке WP финальная раскладка компактна сверху вниз (PLAN E8.5); отступление зафиксировано здесь. Код до W3: `reload(snapshot:)`/`update` при смене состава делали `collectionView.reloadData()` (с кроссфейдом), что сбрасывало live-флипы на лицевую сторону и перезапускало превью папок — при частых обновлениях бейджей флип не наступал никогда. Код после W3: снимок применяется диффом `performBatchUpdates` по ключу «id + признак панели» (панель делит идентификатор с папкой): удаления и вставки, а сдвиг общих элементов UICollectionView делает сам; затем переконфигурируются видимые ячейки (бэйдж, заголовок, содержимое панели) — неизменившиеся элементы сохраняют регистрацию live-плитки и фазу idle-флипа превью. Если порядок общих элементов тоже поменялся (состав + переупорядочивание), снимок применяется через `reloadData`: смешивать `move` с insert/delete в одном batch ненадёжно, а move-ветка остаётся у resize/reorder (`applyIndexMoves`). Кроссфейд смены состава остался (0,2 с) и отключается при Reduce Motion. Заодно `magnetSlotCenters(for:)` считает горизонталь через `TileLayoutEngine.gridMetrics` (как раскладка) — центры слотов совпадают с рамками до пикселя. Решение: дифф-применение — штатный путь; resize/reorder-ветка (`applyIndexMoves` в batch-аниматоре) не менялась. Тесты: `TileGridSnapshotApplicationTests`, `TileGridReduceMotionTests`.

24. **§5 «Режим редактирования»: владелец дима — сетка (E10.4, E8.2, W3, 02.11.2026).** Документ обещал дим остальных плиток до 0,7 в режиме редактирования. Код до W3: `TesseraTileEditCoordinator.applyEditDimming` писал `cell.contentView.alpha` напрямую, а `TesseraTileCell.configure` в конце безусловно ставил `alpha = 1` — дим стирался при любом `update`/resize/drop и переиспользовании ячейки. Код после W3: владелец прозрачности — сетка: `TesseraTileGridView.setEditDimming(_:animated:)` хранит целевые значения, применяет их к видимым ячейкам и после `configure`; ячейка хранит целевую прозрачность и скрытие на время drag, фактическая `alpha = isSourceHidden ? 0 : dimmingAlpha`. Координатор минимально переведён на этот API (считает цели, сетка применяет; длительность и порог Reduce Motion — у сетки). Решение: прозрачность — состояние сетки, а не координатора; скрытие drag сильнее дима. Тесты: `TileGridSnapshotApplicationTests`.

25. **§4 «Live-плитки»: публичная пауза live-контента (E10.4, остаток T1, W3, 02.11.2026).** Документ требовал паузы плиток вне экрана, но не говорил, кто владеет паузой. Код до W3: `TesseraStartPageViewController` вручную обходил `visibleCells` и звал `setLiveTileVisible`, а `grid.update` в обход контроллера показывал новые ячейки видимыми — START за кадром снова флипался (остаток T1 из п. 16). Код после W3: у `TesseraTileGridView` есть публичная пауза `isLiveContentPaused`; она соблюдается в `configure(_:with:isVisible:)` (новые и переиспользованные ячейки не регистрируются видимыми), применяется к видимым ячейкам при переключении и не «воскрешает» скрытые drag-ом; контроллер START включает её на `viewWillAppear`/`viewDidDisappear` вместо ручного обхода. Решение: пауза — состояние сетки, контроллер только переключает. Тесты: `TileGridSnapshotApplicationTests` (пауза после `grid.update` вне экрана и возобновление на START).

26. **§9 «Accessibility»: подпись live-плитки из фронта (E9.8в, W3, 02.11.2026).** Документ обещал label плитки из заголовка + состояний. Код до W3: label брался из `descriptor.title`, а live-view был исключён из accessibility — VoiceOver читал статичный заголовок, хотя на лицевой стороне другой текст. Код после W3: label живой плитки строится из `descriptor.liveContent.frontFace` — `title`, затем `detail` через запятую (пустой фронт откатывается к `title` ярлыка); `value` по-прежнему из бэйджа, точка без числа не озвучивается. Тот же путь — у ярлыка в панели раскрытой папки (он рисуется той же ячейкой). Решение: VoiceOver читает то, что видно на фронте; `TesseraLiveTileView` остаётся декорацией одного элемента. Тесты: `TileGridAccessibilityTests`.

27. **§9 «Accessibility»: Dynamic Type заголовка панели (E10.2, W3, 02.11.2026).** Документ требует масштабирования текста Dynamic Type и проверки, что вёрстка не ломается. Код до W3: шрифт заголовка панели собирался один раз с потолком 28 pt; при смене категории, пока панель вне экрана, шрифт оставался старым. Код после W3: `TesseraFolderPanelCell.makeTitleFont(compatibleWith:)` масштабирует базовый 16 pt по `UIFontMetrics`, потолок ограничен намерением дизайна (28 pt) и высотой строки заголовка панели (`panelHeaderHeight`, 44 pt) — строка не обрезается и на accessibility-размерах; шрифт пересобирается по trait-коллекции панели при показе ячейки и смене категории, а не только по уведомлению сетки. Решение: заголовок панели масштабируется в пределах фиксированной высоты строки; высота панели и внутренняя раскладка не меняются. Тесты: `FolderPanelAnimationTests` (`testPanelTitleFontScalesWithinHeaderHeight`).

28. **§9/§14 «Ярлыки панели раскрытой папки»: активация через `onTap` хоста (E10.4, m6, W3, 02.11.2026).** D17 описывал тап по ярлыку внутри панели как вызов `TileDescriptor.action` (папка остаётся открытой). Код до W3: `TesseraFolderPanelCell.activateTile(at:)` вызывал `tiles[index].action()` напрямую — мимо `onTap`/делегата хоста и даже в режиме редактирования. Код после W3: активация (тап и VoiceOver) идёт общим маршрутом `TesseraTileGridView.handleItemTap` → `onTap` с `.tile(descriptor)`; в режиме редактирования действие не выполняется; закрытие папки тапом по пустому месту панели сохранено. **Breaking для интеграторов:** если хост полагался на прямой вызов `action` из панели, теперь действие нужно обрабатывать по `grid.onTap` (как для плитки сетки). Дополнительно в W3 зафиксированы ограничения: колбэки `onTap`/`onFolderExpansionChanged` синхронные — повторный вход в `reload`/`update`/`openFolder` из них может смешать `reloadData` и batch в одном проходе runloop (m5), реакцию следует откладывать; getter `isScrollEnabled` возвращает фактическое состояние с учётом блокировки панели, поэтому паттерн read-modify-write во время анимации не гарантирует восстановление (m1) — храните собственное намерение. Тесты: `TileGridSnapshotApplicationTests`.

29. **Фикс-раунд W3 по итогам гейта и независимого ревью (M1, M2, m1–m6, n1, n4, n5, 02.11.2026).** По результатам `xcodebuild test` (602 теста, один упавший тест-кейс) и ревью поправлено: **B1** — тест превью папки готовит ярлыкам видимый бейдж (idle-флип невозможен при `.none`, `TesseraFolderMiniTileView.showBadge` — no-op). **M2** — неанимированный путь `reload(snapshot:)`/`update(animated: false)` применяет смену состава внутри `UIView.performWithoutAnimation`: иначе `performBatchUpdates` анимировал insert/delete дефолтной длительностью UIKit (~0,25 с) и нарушал контракт «без анимации»; анимированный путь (кроссфейд) не менялся, добавлен внутренний признак `didApplyLastSnapshotWithoutAnimation` для теста. **M1** — `runDeferredFolderWork` после применения отложенного снимка не исполняет отложенную цель панели в том же стеке, а переоткладывает её на следующий проход runloop: снимок мог уйти в `reloadData` (fallback диффа), и синхронная batch-вставка панели повторила бы класс дефекта «reloadData + batch в одном проходе»; last-wins сохранён, busy-loop нет. **m2** — анимация отложенного снимка пересчитывается в момент применения (окно/Reduce Motion могли измениться). **m3** — неанимированные ветки раскрытия/закрытия доводят layout (`layoutIfNeeded`) перед `.layoutChanged`, чтобы фокус VoiceOver уходил на реально существующую ячейку панели/папки. **m4** — повторный тап по папке в первые ~0,12 с закрытия — цель «открыть снова»: `toggleFolder` при `closing` ставит `pending .open`, `openFolder` при идущем переходе ставит отложенную цель даже если `expandedFolderID` ещё не снят. **n1** — флаги применения снимка сбрасываются в resize/reorder-ветке (не остаются устаревшими). **n4** — комментарий `TileDescriptor.title` уточнён: у live-плиток accessibility label строится из `liveContent.frontFace`. **n5** — тест пиксельного выравнивания проверяет origin/size рамок (кратность `1/scale`), а не центры слотов: центр слота при нечётном юните законно попадает на полпикселя. **m5/m1** зафиксированы как ограничения контракта (см. п. 28): синхронные колбэки нельзя использовать для повторного входа в `reload`/`update`/`openFolder`; getter `isScrollEnabled` возвращает фактическое состояние с учётом блокировки панели. Известное ограничение: предупреждения `[CollectionView] Received layout attributes with an invalid index path` в windowed-тестах — transient-рассинхрон кастомной раскладки при count-changing `performBatchUpdates` (панель/дифф) на границе кадра; не воспроизводится детерминированно, поведение тестов корректно, менять порядок инвалидации раскладки в анимированных переходах панели без runtime-проверки рискованно. Тесты: `FolderPanelAnimationTests` (+M1, +m4), `TileGridSnapshotApplicationTests` (+M2, обновлён B1/n5).

30. **§5 «Перетаскивание»: зоны плитки-папки, центр без удержания, магнит от центра снимка, строгие границы E8.6, «желе» ±1,2° (E10.5-A, E9.5, E9.8а, W4, 02.11.2026).** Документ описывал drag как «снимок едет за пальцем, соседи расступаются», но не фиксировал: поведение плитки-папки как цели, точку отсчёта магнитизма, семантику drop в центр без удержания, амплитуду «желе» и точность границ E8.6. Код до W4: у плитки-папки была только зона add-to-folder (переставить ярлык на место папки было нельзя — drop на папку всегда добавлял внутрь); магнит (`TesseraTileMagnet`) считал расстояние по точке **пальца**, а снимок ставился в центр слота — плитка, взятая не за центр, прыгала до половины плитки; после смещения пальца за допуск удержание E8.6 не перевзводилось до выхода из зоны/смены цели; drop в центр ярлыка без удержания мог зафиксировать **предыдущее** превью перестановки; «желе» фактически было ±1,2° (спека §5 — ±2°). Код после W4: (а) у плитки-папки есть краевые зоны: левая/правая половины (вне центральной зоны) — `.reorder` с базовым индексом папки, центральная зона — add-to-folder только после удержания E8.6 (D14), папка-источник в папку не таскается; (б) магнит считает расстояние от **центра снимка** (`point + grabOffset`), поэтому снимок смещается к центру слота не больше чем на радиус притяжения, а стартовая зона/над-панелью/Reduce Motion остаются как были; (в) после отмены удержания (смещение на допуск или больше) возврат пальца в допуск запускает **новый** отсчёт 600 мс; (г) drop в центр без удержания — возврат на исходное место (no-op), push-превью для центральной зоны не делается; (д) при входе в edit и старте drag раскрытая панель папки закрывается штатным `closeFolder`, drag с ячеек панели (`.folderContent`) не начинается; (е) границы E8.6 строгие: смещение **меньше** 10 pt и удержание **больше** 600 мс. Решение E9.5: семантика «центр без удержания = no-op/отмена» зафиксирована в документации и комментариях E8.6; E9.8а: «желе» остаётся базово ±1,2° (на плитку — коэффициент 0,85–1,15), на ±2° не переходим; границы читаются строго. Уточнение m7 (фикс-раунд W4): no-op-семантика E9.5 относится к центру **ярлыка** (и к центральной зоне плитки-папки, где без удержания drop — тоже возврат на место); панель раскрытой папки — не drop-цель: над `.folderContent` цель `.none`, и drop по ней возвращает ярлык на исходное место. Подсветка «впитывания» сохраняет акцент цели (n5): у центра ярлыка — оранжевый, у центра папки — синий (`.merge`/`.mergeFolder`), отличаются толщина рамки и заливка. При старте drag из long-press раскрытая панель закрывается **мгновенно** (`closeFolder(animated: false)`), чтобы первые кадры drag не шли поверх сдвигающейся раскладки; публичный `beginEditing()` без drag закрывает её анимированно (m3). Тесты: `DragSessionTests`, `TileMergeHoverTests`.

31. **§5 «Перетаскивание»: состояние drag — внешние изменения, deinit/fly-out, двойной unpin, конфигурация на лету, «желе»/дим после reload, `.layoutChanged` (E10.5-B, W4, 02.11.2026).** Документ не описывал гонки состояния drag. Код до W4: внешний `grid.update` во время drag оставлял превью посчитанным от устаревшего `baseSnapshot`, а отмена/`restore` могли откатить сетку к базе и рассинхронизировать её с `TileStore`; `deinit` восстанавливал `autosaves`, но не возвращал скрытую ячейку и не включал `isScrollEnabled`, а fly-out при уже исчезнувшем координаторе оставлял ячейку скрытой; двойной быстрый unpin запускал второй fly-out; смена `controlDiameter` на лету не пересоздавала кнопки (они создаются с диаметром в инициализаторе); после `reloadData` при unpin/создании папки плитки могли замирать без «желе» и терять дим; `.layoutChanged` после unpin/resize не публиковался. Код после W4: (а) модель и применённый снимок сетки сверяются с базой drag — расхождение (внешняя мутация модели или чужой `grid.update`) безопасно отменяет drag, возвращает скрытую ячейку/прокрутку и синхронизирует сетку с **текущим** снимком store (а не с устаревшей базой), внешняя мутация сохраняется; (б) `deinit` и завершение fly-out при уже исчезнувшем координаторе возвращают скрытую ячейку, `isScrollEnabled`, `autosaves`, снимают оверлеи, пустышку, spring и таймеры; (в) unpin получил in-flight guard по tileID: один fly-out, одна мутация, один колбэк; (г) смена конфигурации на лету пересоздаёт контролы, перезапускает «желе» и снимает удержание/магнит; (д) после `render` (unpin, создание папки) «желе» и дим переприменяются к видимым ячейкам; (е) `.layoutChanged` публикуется после unpin/resize/move на следующий проход runloop с ячейкой-фокусом (для unpin — элемент, вставший на место удалённого). M1 (фикс-раунд W4): отложенный сеткой снимок (drag-превью во время анимированного закрытия панели папки, E10.2) при отмене/no-op/`endEditing` заменяется снимком модели даже при совпадающем видимом порядке — `grid.update` перезаписывает pending по last-wins; иначе после завершения перехода сетка применила бы устаревшее превью и разошлась бы с `TileStore`. m3 (фикс-раунд W4): при старте drag из long-press панель закрывается мгновенно, публичный `beginEditing()` — анимированно. Контракт `startDrag` (m2): к моменту захвата снимок сетки обязан совпадать с моделью, иначе drag не начинается (в DEBUG — assertion); долгое нажатие при рассинхронизации не начинает перетаскивание, хосту нужно применять store-снимки. Решение: владелец дима и доступности прокрутки остаётся у сетки (пп. 22, 24), координатор отвечает за восстановление после своей сессии. Тесты: `DragSessionTests`.

32. **§5/§6/§14 «Порядок и папки»: фактический индекс drop, канонизация, экран папки через `onTap` (E10.5-C, W4, 02.11.2026).** Документ обещал, что порядок хранит `TileStore` (§6), а тап по ярлыку в папке вызывает действие (D17). Код до W4: drop и публичный `move` писали `TileStore.move(_:toIndex:)` без числа колонок и отдавали делегату запрошенный индекс, а не фактический (зажатый/канонизированный); встроенный экран папки вызывал `TileDescriptor.action` напрямую в обход `onTap`/делегата хоста. Код после W4: drop и публичный `move` идут через `TileStore.moveItem(_:toIndex:columns:)` (E10.3a), делегат получает **фактический** индекс из хранилища, после drop сетка синхронизируется со снимком store (включая канонизацию порядка E10.15); признак «порядок изменился» для `move` вычисляется **до** мутации (m1, фикс-раунд W4): хост, синхронно применяющий `store.onChange` к сетке, всё равно получает `didMove` и `.layoutChanged`; после unpin и папочных операций вызывается `TileStore.canonicalizeVisibleOrder(columns:)`; тап по ярлыку на экране папки идёт общим маршрутом `grid.onTap` (событие обрабатывает хост один раз, действие выполняет хост — D12), в режиме редактирования не активируется. m4 (фикс-раунд W4): активация выполняется в completion закрытия sheet (как раньше `action`), а не до dismiss, чтобы событие хоста не конфликтовало с уходом экрана; если координатора/сетки уже нет, действие ярлыка выполняется напрямую (fallback). **Breaking для интеграторов:** если хост полагался на прямой вызов `action` из экрана папки, теперь действие нужно обрабатывать по `grid.onTap` (как для плитки сетки; ср. п. 28 для панели раскрытой папки). Активация ярлыка в папке из режима редактирования не выполняется. Тесты: `DragSessionTests`.

33. **§1–§4 «Строки интерфейса по умолчанию»: внутренний источник — SPM-ресурсы en/ru с dotted-ключами (E9.8г, W5, 02.11.2026).** Документ не фиксировал, на каком языке и откуда берутся строки, которые компонент показывает по умолчанию, и что именно из них локализуется. Код до W5: user-facing строки жили литералами прямо в Swift-коде (часть — по-русски, часть — по-английски), локализация таргета не поддерживалась. Код после W5: строки вынесены в ресурсы таргета — `Localizable.strings` в `en.lproj` и `ru.lproj` (объявлены как `resources` в `Package.swift`), по **41 ключу** в каждой таблице; паритет ключей en/ru проверяется тестом. Ключи — стабильные dotted-идентификаторы (`a11y.editing.entered`, `folderScreen.done`, `appsList.pinActionTitle`, `panel.expanded`, …), переводятся только значения. Резолв — через `Bundle.module` (внутренний `TesseraStartScreenStrings`; `@usableFromInline` помечены сам `enum` и его члены, нужные default-аргументам публичного `TesseraAppsListTexts.init`; публичная поверхность модуля не менялась). Ресурсный бандл `TesseraKit_TesseraStartScreen.bundle` — часть пакета: если потребитель скопировал модуль без него, обращение к строке падает с `fatalError` (требование к интеграторам). Локализованный объём — user-facing строки: 34 обращения в `TileEditCoordinator` (VoiceOver-озвучивания, меню/алерты/экран папки, custom actions, названия размеров), 5 дефолтов `TesseraAppsListTexts`, accessibility value «раскрыта» панели в `TileGridView`. **Не в таблицах** — остаются английскими дефолтами/параметрами хоста: `startPageTitle`/`quickPanelTitle`/`applicationsPageTitle` контроллера и `StartScreenStyle` (подписи страниц START/хука/списка), а также тексты, переданные хостом (`TesseraAppsListTexts`, `folderTitle` и т.п.), — они перекрывают значения по умолчанию, но только те строки, которые параметр принимает. При локали устройства, отличной от en/ru, действует fallback — английский (неподдерживаемая локаль не даёт пустую строку или технический ключ). Плюрализация: обычные `.strings` не поддерживают plural-варианты, поэтому словоформы «ярлык» лежат отдельными ключами (`folderScreen.tiles.word.one/few/many`), а правило выбора — в коде (`en` — одна/множественная, `ru` — одна/несколько/много с учётом 11–14); для нового языка нужны свои правила в коде или переход на `.stringsdict`. Диагностика для разработчика (ошибки `TileStore`, `precondition`/`fatalError`, deprecation-сообщение, DEBUG-assertion) намеренно остаётся русскими литералами вне UI-таблиц (allowlist из 8 литералов в `LocalizationTests`). Решение: источник UI-строк — SPM-ресурсы en/ru с dotted-ключами и fallback на английский; публичный API не менялся. Хост-параметры перекрывают только строки, которые принимают; внутренние VoiceOver-строки и строки экрана папки хостом не переопределяются — для нового языка нужны таблицы en/ru и правила плюрализации (или `.stringsdict`).

34. **§5 «Перетаскивание»: трактовка push-физики E8.4 (E8.4, E9.11, W5, 02.11.2026).** Документ (E8.4): «плитка-цель и всё ниже неё плавно сдвигаются вниз на высоту перетаскиваемой». Код: во время drag модель не меняется; порядок соседей — превью `TileLayoutEngine.previewOrder`, применяемое в сетку снимком (`grid.update`); перетаскиваемая встаёт в слот цели, а цель и плитки ниже переупаковываются строго компактно (п. 5) — освободившееся место может подтягивать часть плиток вверх. То есть это push-эффект через перестановку и переупаковку, а не сдвиг на фиксированную высоту: запись порядка в `TileStore` происходит один раз на drop, отмена возвращает снимок на момент захвата. Решение: E8.4 читать как «push-эффект через preview-порядок»; отдельной анимации сдвига на высоту перетаскиваемой нет.

## Отступления реализации (E11, 02.11.2026)

35. **§5/§14 «Папки: размер новой папки, вынос из папки, цель полёта снимка» (E11.2–E11.4, 02.11.2026).** (а) E11.4 **(отменено E12.2, см. п. 41)**: `TileStore.createFolder` больше не ставил `.medium`, а наследовал актуальный размер ярлыка-цели (сохранённый в `sizes` либо из дескриптора): папка занимает его слот, соседи не переупаковываются. Кламп по числу колонок не нужен — ярлык уже помещался в сетку с этим размером, слот не меняется; схема персистентности не менялась (размер папки хранится в её записи, как и раньше). (б) E11.2: ярлык, вынесенный из папки на рабочий стол (`moveBetweenFolders(_:to: nil)`), встаёт не в конец сетки, а сразу после папки-источника; если папка распалась (вынесен последний ярлык), ярлык занимает её место. Публичный API расширен аддитивно: `TileStore.moveBetweenFolders(_:to:at:)` и такой же метод координатора принимают необязательный индекс в пространстве видимого снимка (как `moveItem`, значение зажимается); прежние сигнатуры сохранены. Порядок чтения под число колонок по-прежнему приводит `canonicalizeVisibleOrder`/координатор, фокус VoiceOver — на вынесенном ярлыке. Делегат `didMove(toFolder:)` индекс не получает (аддитивный вариант с индексом — п. 36). (в) E11.3: в `dropIntoNewFolder` рамка новой папки читается после канонизации и `render(animated:)`, поэтому снимок схлопывается в плитку-папку, а не в слот плейсхолдера; рамка цели доступна тестам через внутренний `lastCollapseTargetFrame`.

36. **§5 «Папки: ярлык из панели в режиме редактирования» (E11.1, 02.11.2026).** Документ и код до E11 не давали вытащить ярлык из папки перетаскиванием: `beginEditing` закрывал панель, тап по папке в edit раскрытия не запускал, долгое нажатие по панели только входило в edit. Решение (вариант A): (а) тап по папке в edit открывает нативную панель D17 и режим не прерывает — `handleItemTap` ведёт себя одинаково в обоих режимах: `folderTapHandler` вызывается и в edit (`true` отменяет раскрытие и `onTap`), иначе приходит `onTap` и панель переключается; `beginEditing()` по-прежнему закрывает уже открытую панель. (б) долгое нажатие по иконке панели в edit мгновенно закрывает панель (`closeFolder(animated: false)`, как в m3) и поднимает ярлык: источник drag — папка (`TesseraTileDragSession.sourceFolderID`), снимок иконки берётся до закрытия, смещение захвата считается от рамки иконки. Модель за время drag не меняется: сетка показывает **отображаемый** снимок — ярлык вынут из состава папки и вставлен отдельным ярлыком сразу после неё (его слот/пустышку и push-превью `TileLayoutEngine.previewOrder` обслуживает обычная машина E8.4); сверка с моделью (`modelMatchesBase`) идёт по реальному снимку (`modelBaseSnapshot`). (в) цели: сетка/пустое место — вынос на позицию превью `TileStore.moveBetweenFolders(_:to: nil, at:)` (индекс уменьшается на единицу, если папка из одного ярлыка распадается и стояла перед ярлыком), порядок читается под число колонок, фокус VoiceOver — на ярлыке; центр **другой** папки с удержанием E8.6 — `moveBetweenFolders(_:to: folder)`; без удержания — no-op; центр обычного ярлыка для такого источника папку **не создаёт** (двухшаговое создание требует ярлыка на сетке) и работает как перестановка; центр родной папки, панель, отмена и отказ одобрения хоста — возврат ярлыка в папку без изменения модели (снимок «впитывается» в рамку папки). Если вынесен последний ярлык, папка распадается (поведение `TileStore`). Перестановка внутри папки — вне объёма. (г) Делегат: добавлен `didMove(_:toFolder:atIndex:)` с фактическим индексом при выносе (`nil` — при переносе в папку); координатор вызывает **только его**, реализация по умолчанию пересылает событие в прежний `didMove(_:toFolder:)`, поэтому прежние делегаты продолжают получать событие, а новые — индекс (ровно один из двух). Протокольная реализация по умолчанию именно пересылающая, а не пустая: иначе координатор не знал бы, какой из двух колбэков реализован делегатом. Новая строка локализации — причина отказа переноса (`a11y.grouping.reason.moveDenied`, en/ru). Reduce Motion, haptics и озвучивание — как у остальных папочных drop'ов.

37. **§9 «Accessibility»/§5 «Папки»: custom actions папок и атомарное создание папки (E11.5, E11.6, 02.11.2026).** (а) E11.5: в режиме редактирования ячейка ярлыка на сетке получает к «Открепить»/«Изменить размер» пункты «Добавить в папку <название>» — по одному на существующую папку, не больше `TesseraTileEditCoordinator.maxFolderActions` (6, первые папки в порядке сетки; пустое название заменяется `folderTitle` конфигурации, затем общей подписью папки). Ярлыки панели раскрытой папки получают «Убрать из папки» (вынос сразу после папки через `moveBetweenFolders(_:to: nil)`) и «Переместить в папку <название>» по одному на другую папку (тот же кап). Все пункты вызывают публичные `addToFolder`/`moveBetweenFolders` координатора, то есть проходят функцию одобрения хоста (D14), озвучивание и фокус; отказ возвращает `false` и даёт `didFailGrouping`. У плитки-папки новых действий нет. Сверка действий идёт по подписи (плитка + состав папок), поэтому новая папка появляется в уже настроенных ячейках; ярлыки панели получают действия отложенной сверкой (внутренний шов сетки `panelShortcutsDidConfigure`), выход из edit снимает всё. «Создать папку с…» **не реализовано**: нужен выбор второго ярлыка (picker), для VoiceOver это отдельный UI вне простого объёма; создать папку без drag можно публичным `createFolder(withTile:)`. Строки: `a11y.action.addToFolderFormat`, `a11y.action.removeFromFolder`, `a11y.action.moveToFolderFormat` (en/ru). (б) E11.6: создание папки drop'ом (два одобряемых шага D14) атомарно: внутренний `TileStore.createFolder(withTile:adding:title:)` применяет первый шаг только в памяти, спрашивает хост о втором и при отказе возвращает слот цели и убирает запись папки — без `onChange`, автосохранения и `objectWillChange` для промежуточного состояния и отката; при успехе уведомление одно. Хост по-прежнему видит оба одобрения (`.createFolder`, затем `.addToFolder`; при втором одобрении папка уже содержит целевой ярлык). Координатор шлёт `didCreateFolder` только после успеха обоих шагов, непосредственно перед `didAdd`; при отказе второго шага делегат получает только `didFailGrouping(.addToFolder, …, folderID: nil)` (папки не существовало), модель — ровно как до drop'а. Текст причины `a11y.grouping.reason.tileAddDenied` изменён на «добавление ярлыка в новую папку запрещено». Публичный API не менялся (новый метод хранилища internal).

38. **§5 «Drag: цель определяется по базовой раскладке» (E11.7, 02.11.2026).** Документ не уточнял, по каким рамкам ищется цель под пальцем; код искал элемент и считал центр (25%) по рамкам сетки, уже сдвинутым push-превью. Подтверждено оконным тестом: плитка/папка, уехавшая из-под пальца, оставляла палец над пустышкой (`.none`), поэтому зона центра (группировка/добавление в папку, E8.6) была недостижима при подходе в сторону сдвига, а `.group`/`.folder` срабатывали по кадрам, которых пользователь не видел. Решение: `updateHoverTargets` решает цель по **базовой** раскладке — раскладке `session.baseSnapshot.items` (тот же порядок, что у `.reorder`/`baseIndex`); рамки считает `TesseraTileGridView.baseContentFrames(for:)` той же геометрией, что `TesseraTileCollectionViewLayout` (пиксельные края, `gridMetrics`, `pack` по ужатым размерам, RTL), в координатах контента и кэшируются в сессии; кэш перестраивается при смене ключа геометрии (размер, колонки, поля, зазор, масштаб, направление), а `contentOffset` учитывается на каждом шаге переводом в координаты сетки (кадры автопрокрутки видят актуальное смещение). Над собственным базовым слотом перетаскиваемого элемента цель — `.none` (превью остаётся прежним, поведение «c»). Подсветка цели рисуется по-прежнему на видимой (сдвинутой) рамке. Пока папка раскрыта (в т. ч. во время анимированного закрытия панели) раскладка сетки не совпадает с базовой, и действует прежний хит-тест по рамкам сетки; drag из панели (E11.1) работает по базе с синтетическим ярлыком. Гистерезис зон не вводился. Покрыто `DragSessionTests` (репро с папкой, граница центра, `contentOffset`).

39. **§5 «Drag ярлыка из панели: раскладка во время drag» (E12.1, 02.11.2026).** Сообщение «ярлык вынесен в дыру и попал в соседнюю папку» не воспроизведено ни в 4, ни в 5/6 колонках, поведение не менялось. Фиксируем свойство, на которое легко ошибиться при ручной проверке: во время drag из панели сетка показывает отображаемый снимок (папка-источник без ярлыка плюс синтетический ярлык после неё), поэтому упаковка отличается от модельной — «дыра» модели занята другой плиткой, а соседние плитки могут оказаться вплотную к ней. Цель по-прежнему выбирается по точке пальца на базовой раскладке (E11.7), а не по центру снимка: при крайнем хвате иконки панели палец может стоять над центром другой папки, пока снимок (магнит) выглядит в пустой клетке. Удержание над другой целью сбрасывается при уходе пальца (покрыто тестами `DragSessionTests`, E12.1).

40. **§5 «Удержание E8.6: якорь переносится при смещении» (E12.3/E12.1, 03.11.2026; меняет E8.6/E9.8а/E10.5-A3).** Гипотеза «снимок с магнитом расходится с пальцем» не подтвердилась: притяжение E8.9 выключено над целями `.folder`/`.group`, поэтому у центра другой папки снимок стоит под пальцем при любом хвате иконки панели (радиус 28 pt, хват за центр и углы; E12.1 с краевым хватом в 4/5/6 колонках в соседнюю папку не попадает). Причина несрабатывания слияния — контракт трекера: якорь допуска (10 pt) ставился на первой точке центральной зоны цели, после смещения на допуск или больше трекер уходил в `cancelled` и перевзводился только при возврате к **старому** якорю (E10.5-A3). Палец, идущий к центру несколькими шагами и остановившийся, слияния не получал (то же у drag с сетки), а drop по `.folder` без готовности оставлял только то, что дало push-превью. Решение пользователя: удержание — «палец остаётся в пределах допуска (<10 pt) дольше порога (>600 мс), **считая от последнего заметного движения**». Смещение от якоря на допуск или больше отменяет прежнее удержание (в т. ч. уже выдержанное, подсветка «впитывания» откатывается) и сразу начинает новое: якорь переносится в текущую точку, отсчёт 600 мс идёт заново (`armed`), таймер координатора пересоздаётся. Состояние `cancelled` убрано. Остаются без изменений: строгие границы (<10 pt, >600 мс), смена цели — новое удержание, `reset()` — `idle`, уход из зоны сбрасывает удержание, Reduce Motion, haptic/озвучивание — только когда удержание реально выдержано. Следствия: постоянное движение (каждый шаг ≥10 pt) готовности не даёт; возврат к старой точке после смещения — тоже смещение, то есть новый отсчёт. Остаточное превью: drop по `.folder`/`.group` без готовности идёт через `returnAfterNoOpDrop` → `restore()` (сетка синхронизируется с моделью), и оконный тест `testNotReadyDropOnFolderCenterLeavesNoPushPreview` подтверждает порядок сетки = модели после такого drop'а — отдельный дефект кодом не воспроизведён; наблюдавшееся в ручном прогоне, вероятно, было следствием несработавшего слияния (ярлык возвращается на слот анимированно) и не менялось. Покрыто `TileMergeHoverTests` (якорь, постоянное движение, возврат к старому якорю) и `DragSessionTests` (14-шаговый заход с панели и с сетки, постоянное движение, возврат, слияние с магнитом, краевой хват).

41. **§3/§5 «Папка — всегда medium» (E12.2, 03.11.2026; отменяет E11.4).** Решение пользователя: в Windows 10 Mobile папка всегда средняя плитка 2×2, независимо от размера ярлыка-цели. Поэтому `TileStore.createFolder(withTile:)` и атомарное `createFolder(withTile:adding:title:)` снова создают папку размера `.medium` (константа `TileStore.newFolderSize`); папка из wide/large цели замещает её слот средней плиткой, соседи переупаковываются строго компактно (п. 5), каноничный порядок и рамка полёта снимка (`lastCollapseTargetFrame`, п. 35в) берутся после канонизации и `render`. Схема персистентности не менялась; при загрузке сохранённый размер папки **не нормализуется**: папку можно менять в размере (`resize`/«Изменить размер» работают и для папок, как раньше), поэтому записанный размер — осознанный выбор пользователя, а записи, оставшиеся от короткой жизни E11.4, неотличимы от него; терять размер без ведома пользователя хуже, чем показать один раз папку нестандартного размера. Фраза §3 «размеры плиток 1×1, 2×2, 4×2, 4×4» относится к ярлыкам; новая папка всегда 2×2. Симптом из ручного прогона (слияние на центр wide/large цели с удержанием ~1,5 с не создавало папку) на текущем коде **не воспроизводится**: центральная зона (25%-й отступ от базовой рамки) и `.group` не зависят от размера цели, удержание и `dropIntoNewFolder` — тоже; тест `testMergeOnTargetCenterCreatesMediumFolder` перебирает wide/large/small цели (источник medium/small, до и после цели, 14 шагов и «прыжок») и проходит. Вероятная причина — контракт трекера до E12.3 (п. 40): на большой центральной зоне wide/large палец неизбежно сдвигается больше допуска, и без перевзвода удержание не набиралось; превью «слот под целью» и возврат на старое место — это drop `.group` без готовности (`restore()`), а не отдельный дефект. Проверено на родителе коммита E12.3: 14-шаговый заход на центр цели готовности не даёт.

42. **§5 «Кнопки редактирования: клип и вид» (E12.4/E12.5, 03.11.2026).** Кнопки «открепить»/«размер» были подвью самой сетки, а границами `bounds` обрезалась только коллекция, поэтому у плитки, частично ушедшей под верхний/нижний край, кнопка рисовалась поверх status bar. Теперь кнопки лежат в контейнере `TesseraTileEditControlsHostView` (`clipsToBounds`, рамка = `bounds` сетки, `zPosition` 200, сам касания не перехватывает) и режутся по той же границе, что и плитка; полностью вне `bounds` кнопки скрыты, как раньше. Вид (в духе Windows 10 Mobile): диаметр = ≈ 24 % меньшей стороны плитки, не меньше 20 pt и не больше `controlDiameter` (теперь это потолок: малая плитка ≈ 21 pt, средняя и больше — 28 pt); центр кнопки у угла плитки, выступ за рамку 6 pt по каждой оси (зазор плиток по умолчанию 8 pt, поля сетки ≥ 16 pt — на соседей и за край кнопка не заходит; при нулевом зазоре возможно перекрытие кромки соседа); светлая заливка с тёмным символом, кольцо 1 pt и тень — контраст на светлых и тёмных плитках в обеих темах (кольцо — динамический цвет, пересчитывается в `traitCollectionDidChange`). Видимая кнопка мелкая, но зона касания ≥ 44 × 44 pt: `hitTest`/`point(inside:)` оверлея считают попадание по расширенным зонам. Остаточное: на малой плитке кнопка может задеть угол иконки/конец длинной подписи; Reduce Motion, VoiceOver (кнопки не accessibility-элементы, действия — custom actions) и RTL (кнопки зеркалятся) без изменений.
43. **§9 «Dynamic Type заголовков плиток» (E12.6, 03.11.2026).** На accessibility-размерах шрифт подписи плитки (12/14/17 pt × масштаб категории) вырастал до ~30 pt на плитке 73 pt: «Календарь» рвался посреди слова, подписи малых плиток усекались. Теперь `TesseraTileCell` собирает шрифт с потолком `max(базовый, 20 % меньшей стороны плитки)` (`UIFontMetrics.scaledFont(maximumPointSize:compatibleWith:)`, шрифт пересобирается при смене категории, bucket'а или потолка), а в раскладке подгоняет его под ширину: если самое длинное слово не помещается, шрифт уменьшается до 0,6 базового; если и так не помещается — одна строка с `byTruncatingTail` (многоточие, а не разрыв по символам). `accessibilityLabel` остаётся полным. Заголовок панели папки уже ограничен высотой строки (п. 27). Подсказка и кнопка «Готово/Изменить» — часть Example-хоста, не библиотеки: на accessibility-размерах подсказка скрыта, блок ограничен `xxxLarge`, а его измеренная высота задаёт нижнее поле `contentInsets` сетки, поэтому последний ряд плиток прокручивается выше блока. Остаточное: заголовок не резервирует место под кнопку resize в нижнем углу плитки в edit-режиме (угол 6 pt выступа + заглушка ~15 pt внутрь); Reduce Motion, VoiceOver и RTL без изменений.

44. **§3/§5 «Мелочи ручного прогона: название папки, заголовок панели, зазор панели, unpin папки, тап после свайпа» (E12.7, 03.11.2026).** (а) Название: новая папка раньше создавалась с пустым названием (`folderTitle` по умолчанию `""`), плитка была без подписи, а у панели — без заголовка. Теперь значение по умолчанию живёт в строках модуля (`folderScreen.defaultTitle`: «Папка»/«Folder», en/ru, без литералов в Swift), а не в конфигурации: координатор подставляет его на обоих путях создания (`createFolder(withTile:title:)` и drop ярлыка на ярлык), `TesseraTileEditConfiguration.folderTitle` его перекрывает; `TileStore` по-прежнему допускает пустое название. Папки с пустым названием (из старого хранилища или созданные хостом через store) подписываются тем же значением на плитке, в панели и в accessibility. (б) Регистр: заголовок панели приводился к нижнему регистру («работа» при «Работа» на плитке) — это был код-комментарий D17, а не требование документа или решение пользователя; приведение снято, плитка и панель показывают название как набрано (если нужна WP-подача строчными — это решение пользователя, применять к обоим местам сразу). (в) Зазор между высоким соседом и панелью — следствие п. 11 (E10.1): панель встаёт под «полосой папки» (строки папки плюс плитки, начинающиеся в них и уходящие ниже), зазор от нижней кромки полосы до панели равен `itemSpacing`; пустота остаётся под более короткими плитками полосы (например, под папкой рядом с высокой плиткой). Не дефект раскладки, поведение сохранено (альтернатива — вклинивать панель под короткие плитки, но высокий сосед тогда пересёк бы панель). (г) У плитки-папки нет кнопки «открепить» по дизайну: папка существует, пока в ней есть ярлыки (опустевшая распускается), у неё только «размер» (`configure(canUnpin:canResize:)` у контролов); ярлыки открепляются из панели/меню. (д) Тап после свайпа: `UICollectionView` присылает `didSelect` на отпускании, даже если палец ушёл далеко, когда его собственный пан не начался (горизонтальный свайп по вертикальной сетке, хост без пейджера). В полном `TesseraStartScreenViewController` горизонталь забирает пейджер и отменяет касание, но в самой сетке защиты не было. Теперь на коллекции стоит пассивный `TesseraTileTapSlopRecognizer` (никогда не распознаётся, не задерживает и не отменяет касания; допуск 10 pt в координатах окна, признак живёт до следующего касания), а `didSelectItemAt` игнорирует касание, ушедшее дальше допуска; активация VoiceOver и жест панели папки (штатный `UITapGestureRecognizer` со своим допуском) не затронуты. Проверено на симуляторе в Example. Тесты: `FolderTitleAndTapSlopTests`.

45. **§5 «Каноничный порядок модели перед edit/drag» и кнопки без перелёта (E12.10/E12.9, 03.11.2026).** Ручной прогон (слияние `Почта → Настройки` одним жестом из обычного режима) дал папку в конце сетки и сдвиг «Работы» вверх. Причина — не база хит-теста (E11.7) и не снимок/render во время `beginEditing`, а **неканоничный порядок модели**: хост (сид Example: `createFolder` без колонок) оставил малую плитку последней в `gridOrder`, упаковка подняла её в «дыру» справа от среднего ярлыка, и видимый порядок разошёлся с порядком модели. Цель и подсветка считаются по базовой раскладке и были верны, но drop работает по слотам модели: `createFolder(withTile:adding:)` заменяет слот цели в `gridOrder` (последний), поэтому папка осталась в конце. Решение: координатор канонизирует порядок (`TileStore.canonicalizeVisibleOrder(columns:)`) на входе в edit (после закрытия панели) и в `handleLongPress` до захвата базы drag'а; если сетка до этого показывала модель, она синхронно подтягивается к ней (`syncGridWithModel` без анимации, `layoutIfNeeded`) — видимая раскладка не меняется, перестановка касается только модели; при расхождении, принесённом хостом, по-прежнему срабатывает m2-проверка на захвате. Документированный контракт «после `setCatalog`/`load()`/операций без колонок хост вызывает канонизацию» остаётся, координатор лишь не полагается на него. Возможно, это же причина E12.1 («дыра» модели занята другой плиткой) — не доказано. Кнопки (E12.9): «влёт из левого верхнего угла» наблюдался при возврате плитки после отпускания long-press'а — оверлей пересоздавался анимированным проходом с нулевой рамкой; теперь он создаётся сразу на месте плитки, а анимация переезда существующих кнопок отключается при Reduce Motion. Покрыто `DragSessionTests` (старт из обычного режима, канонизация без видимых изменений) и `TileEditControlsTests`.

46. **§5 «Drag: позиция drop'а над пустым местом» (E12.1, 03.11.2026).** Подтверждённое поведение: ярлык, вынесенный из панели, «падает в первое свободное место», выбрать позицию нельзя. Две причины. (а) Хит-тест E11.7 находит цель только над плитками; над пустым местом (дыра, зазор между плитками, область под плитками) цель была `.none`, и превью оставалось в слоте «сразу после папки» — для drag по сетке то же самое. (б) Раскладка строго компактная (§3, E8.5): ярлык, помещающийся в дыру, упаковщик кладёт в первую подходящую дыру независимо от индекса в порядке, поэтому «позиция» drop'а — это индекс порядка, а не пиксели, и выбрать конкретную дыру нельзя (это возможно только с настоящими пустотами, как в W10M, — вопрос Q6 в STATE.md, не решён). Решение по (а): над пустым местом цель — `HoverTarget.slot(i)`, где `i` — позиция вставки среди остальных элементов базового порядка (`0 ... count`). Её определяет клетка пальца `(строка, колонка)` в базовой раскладке (той же, что у хит-теста; сам элемент стоит на базовом месте, в счёт не входит): элемент встаёт сразу после последней плитки, чей левый верхний угол не позже этой клетки в порядке чтения; правее последней плитки и под сеткой — в конец, выше первой строки — в начало, в дыре — между плитками, которые она разделяет по порядку чтения; зазор между клетками принадлежит клетке слева/выше. Над плиткой по-прежнему E8.4 (`.reorder`: перетаскиваемая встаёт на слот цели), над собственным базовым слотом — `.none` (превью не меняется, «c»). Превью (`TileLayoutEngine.previewOrder(items:draggingID:insertionIndex:)`) следует за пальцем и анимируется как обычное push-превью; drop читает индекс из превью (`previewIndex(of:)`) и для выноса из папки (`moveBetweenFolders(_:to: nil, at:)`), и для обычной перестановки (`moveItem`), поэтому ярлык ложится ровно в показанный кадр (после канонизации порядка раскладка та же). На подъёме превью не трогается, пока палец не сместится больше чем на 12 pt от точки захвата (`emptySlotActivationDistance`): иконка панели после её закрытия обычно стоит над пустым местом, и слот не должен «убегать» из-под пальца в тот же кадр. Хит-тест E11.7, зоны E8.6 и магнит E8.9 не менялись; RTL — клетка считается в логических координатах. Покрыто `DropSlotTests` (конец, зазор между плитками, выше первой строки, под плитками, дыра, распад папки из одного ярлыка, обычный drag, RTL, подъём) и адаптированными `DragSessionTests`.
